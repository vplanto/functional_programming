> 🎮 **Наскрізний курсовий проєкт:** Розробка реактивного, безстанового (stateless) автопілота для швидкісного тунельного раннера з використанням парадигми **MISD (Multiple Instruction, Single Data)**, мажоритарного голосування та механізмів **Backpressure** при експоненційному прискоренні часу.

## Експрес-опитування та розминка

<details>
<summary>1. Чому під час розгону гри до 10 000 дій/сек звичайний об'єктно-орієнтований підхід із блокуваннями призведе до загибелі героя?</summary>

Якщо на кожну подію синхронізувати спільний стан через м'ютекси або `synchronized`, потоки витрачатимуть більше часу на перемикання контексту (Context Switching) та очікування локів, ніж на обчислення. Часовий бюджет на крок впаде до мікросекунд, бот пропустить тік і розіб'ється об першу ж стіну.
</details>

<details>
<summary>2. Як чисті функції та структурне розділення пам'яті (Structural Sharing) у Scala рятують від пауз Garbage Collector (GC)?</summary>

Постійне виділення нових мутабельних масивів або об'єктів створює гігабайти короткоживучого сміття в Young Generation JVM. Це викликає Stop-the-World паузи GC. Незмінні персистентні структури даних Scala перевикористовують спільні вузли дерев пам'яті, зводячи навантаження на GC майже до нуля.
</details>

## 1. Концепція гри: Світ тунелю та геометрія зрізу 3×3

Герой невпинно біжить уперед нескінченним 3-смуговим тунелем. Кожен крок дистанції — це поперечний зріз у вигляді **матриці 3×3 (9 комірок простору)**: 3 смуги руху та 3 рівні висоти.

```text
                  [Lane: Left]         [Lane: Center]        [Lane: Right]
Висота 2 (Верх):  [    .     ]         [  HighBeam  ]        [     .      ]  <- Стеля
Висота 1 (Центр): [   Coin   ]         [     .      ]        [  MidLaser  ]  <- Рівень очей/грудей
Висота 0 (Низ):   [ LowHurdle]         [     .      ]        [     .      ]  <- Рівень землі
                                            [@]
                                   (Герой біжить по центру)
```

### Фізика висот та допустимі дії:

Кожна смуга на поточному кроці може містити перешкоди на висотах 0, 1 або 2:

| Де перешкода | Допустимі дії для порятунку | Заборонені дії (аварія/crash) | Фізика ситуації |
| :--- | :--- | :--- | :--- |
| **Висота 0 (Низ)** | **`Jump`** | `KeepRunning`, `Duck` | Бар'єр на дорозі. Тільки стрибок рятує. Біг або присідання — падіння. |
| **Висота 1 (Центр)** | **`Duck`** або **`Jump`** | `KeepRunning` | Перешкода на рівні грудей. Треба **прослизнути знизу (`Duck`)** або **перестрибнути зверху (`Jump`)**. |
| **Висота 2 (Верх)** | **`KeepRunning`** або **`Duck`** | **`Jump`** | Низька балка зі стелі. Біжи або присідай. **Стрибати заборонено** — розіб'єш голову об стелю. |

### Комбінації та інваріант розв'язності (No Dead-End Invariant):
1. **Комбінація [Висота 0] + [Висота 2] на одній смузі:**  
   Висота 0 вимагає `Jump`, а Висота 2 забороняє `Jump`. Залишатися на смузі неможливо — герой зобов'язаний змінити смугу (`MoveLeft` або `MoveRight`).
2. **Глуха стіна (0 + 1 + 2):** Смуга повністю заблокована на всіх рівнях.
3. **Гарантія прохідності (Reachability Invariant):**  
   Рушій **ніколи не блокує всі 9 точок одночасно**. На кожному кроці генератор гарантує існування щонайменше одного безпечного коридору для виживання.

### Доменна модель у Scala 3:
* **Смуги:** `enum Lane { case Left, Center, Right }`
* **Рівні висоти:** `enum Height { case Low, Mid, High }` (0, 1, 2)
* **Положення тіла героя:** `enum Stance { case Running, Jumping, Ducking }`
* **Дії героя:** `enum Action { case MoveLeft, MoveRight, Jump, Duck, KeepRunning }`
* **Вміст комірки:** `enum CellItem { case Empty; case Obstacle; case Coin(value: Int) }`

## 2. Режими роботи Engine (Поступова розробка)

Навчальний рушій (у проєкті `23_runner`) надає 4 режими запуску для покрокового освоєння складності:

1. **`--mode=sandbox` (Калібрування моторики):**  
   3 абсолютно чисті смуги без перешкод і монет. Перевірка базових відповідей бота: ліво, право, стрибок, присідання. Фіксація кількості виконаних рухів та захист від виходу за межі смуг.
2. **`--mode=collector` (Збирач монет):**  
   У тунелі рандомно з'являються монети на висотах 0, 1, 2. Забіг триває фіксований час/кількість тіків. Engine рахує зібрані монети та ефективність траєкторії.
3. **`--mode=obstacles` (Смуга перешкод на стабільній швидкості):**  
   Генерація перешкод із перевіркою розв'язності. Швидкість комфортна (100 мс на тік). Перевірка алгоритмів ухилення та права вето при загрозі аварії.
4. **`--mode=benchmark` (Гіперприскорення та Backpressure):**  
   Повний бойовий режим. Час на прийняття рішення експоненційно скорочується ($100\text{мс} \to \dots \to 500\text{мкс}$). Якщо бот не відповів у межах вікна — дефолтний хід `KeepRunning` та фіксація `Timeout`.

Додаткові системні прапорці:
* **`--seed=<Long>`** — псевдовипадкове зерно генератора для 100% відтворюваності тунелю у всіх студентів.
* **`--step`** — покроковий режим тіків для дебагу та траблшутингу без тайм-аутів.
* **`--out=<file.json>`** — експорт журналу забігу для візуалізатора.

## 3. Архітектура автопілота: Тріада MISD

Героєм керує **реактивний консиліум із трьох паралельних алгоритмів**:

```
                  [Стрім подій тунелю (перешкоди та бонуси попереду)]
                                           │
         ┌─────────────────────────────────┼─────────────────────────────────┐
         ▼                                 ▼                                 ▼
  [Алгоритм 1]                      [Алгоритм 2]                      [Алгоритм 3]
  «Охоронець рефлексів»             «Жадібний збирач»                 «Стратег горизонту»
  (Collision Reflex)                (Coin Hunter)                     (Lookahead Planner)
  Складність: O(1)                  Складність: O(K)                  Складність: O(N)
  Фокус: дистанція < 5 м.           Фокус: де лежать монети.          Фокус: прорахунок на 3 кроки,
  Голосує за порятунок життя.       Голосує за максимальні очки.      щоб не потрапити в комбо-пастку.
         │                                 │                                 │
         └─────────────────────────────────┼─────────────────────────────────┘
                                           ▼
                               [Мажоритарний Арбітр]
                     (Право абсолютного вето в Охоронця +
                      мажоритарний вибір напрямку руху)
```

1. **«Охоронець рефлексів» ($O(1)$):** Блискавичний фільтр безпеки. Бачить загрозу впритул. Має право **абсолютного вето** на самогубні дії.
2. **«Жадібний збирач» ($O(K)$):** Тягне героя на смугу з найбільшою кількістю монет.
3. **«Стратег горизонту» ($O(N)$):** Оцінює наслідки кроку. Якщо стрибок під стелю або рух у смугу 0+2 веде у глухий кут — стратег блокує цю дію.
4. **Мажоритарний Арбітр:** Зводить голоси докупи з урахуванням вето безпеки.

## 6. Контрольні питання для самоперевірки

<details>
<summary>1. Чому комбінація перешкод на Висоті 0 та Висоті 2 в одній смузі вимагає негайного MoveLeft або MoveRight?</summary>

Висота 0 вимагає обов'язкового стрибка (`Jump`), щоб не розбитися об бар'єр на землі. Але Висота 2 містить балку зі стелі і суворо забороняє `Jump`. Оскільки герой не може одночасно стрибати і не стрибати, єдиний спосіб вижити — змінити смугу руху.
</details>

<details>
<summary>2. Чому Арбітр повинен давати Охоронцю право вето, а не просто рахувати середній бал дій?</summary>

Якщо два алгоритми голосують за `KeepRunning` (бо там лежить дорога монета), а Охоронець бачить перешкоду на Висоті 1 прямо по курсу — усереднення голосів призведе до миттєвої загибелі. У надійних безперервних системах безпекові інваріанти мають абсолютний пріоритет.
</details>
