## Експрес-опитування та розминка

<details markdown="1">
<summary>1. Чому валідація даних через throw new IllegalArgumentException() — це катастрофа для High-Load сервісу?</summary>

Кожного разу, коли JVM створює виняток, вона викликає нативний метод ядра `fillInStackTrace()`. Цей метод заморожує потік і покроково сканує всю глибину стеку викликів, щоб побудувати текстовий стек-трейс. На 100 000 невалідних запитів процесор спалює понад 95% ресурсів не на бізнес-логіку, а на запис імен файлів і номерів рядків! Функціональний `Either` повертає звичайний легковажний об'єкт у купі, працюючи у 50–100 разів швидше.
</details>

<details markdown="1">
<summary>2. Чому опціональне призначення платежу має бути Option[String], а не String зі значенням null?</summary>

Тому що тип `String` не дає гарантій відсутності `NullPointerException`. Поле `Option[String]` робить наявність або відсутність коментаря **чесним контрактом на рівні системи типів**: компілятор просто не дозволить викликати `.trim` або `.toUpperCase` безпосередньо, змушуючи розробника безпечно обробити обидва варіанти через `.map` або `.getOrElse`.
</details>

<details markdown="1">
<summary>3. У чому перевага конструювання бізнес-логіки зі списку функцій `List[Transaction => Transaction]` замість одного монолітного методу?</summary>

Принцип відкритості/закритості (Open-Closed Principle): ви можете додавати нові правила (наприклад, святковий кешбек або комісію для юросіб), просто додавши ще одну чисту функцію до списку, не чіпаючи і не ризикуючи зламати вже протестований код попередніх правил.
</details>

## 1. Архітектурний кейс: «Нічний краш банку від невідомого символу»

**Контекст:** Фінтех-стартап запустив обробник вхідних виписок у форматі CSV.  
Розробники написали класичний імперативний сервіс на Java/Spring:

```java
// ❌ Типовий імперативний підхід з Exception для валідації:
for (String line : fileLines) {
    try {
        Transaction tx = parseAndValidate(line); // кидає IllegalArgumentException якщо сума <= 0
        processPayment(tx);
    } catch (Exception e) {
        logger.error("Збій рядка", e); // Кожен збій породжує важкий стек-трейс
    }
}
```

### Що пішло не так:
1. Шахраї запустили скрипт, який засипав шлюз 500 000 запитів із від'ємними сумами (`amount = -100`) та битими адресами пошти.
2. Програма не впала з помилкою компілятора, але на кожному запиті JVM ініціалізувала дорогий `IllegalArgumentException`.
3. Виклики `fillInStackTrace()` наглухо забили всі ядра процесора. Час відповіді шлюзу підскочив з 5 мс до 12 секунд.
4. Легітимні платежі звичайних користувачів почали відвалюватися за тайм-аутом.
5. Більше того, один із парсерів містив помилку: для порожнього коментаря він повернув `null`, що через два кроки викликало `NullPointerException` усередині транзакції на $50 000, яка зависла в невизначеному стані.

**Рішення:** Повна відмова від `Exceptions for Control Flow` на користь **Railway-Oriented Programming (Either)** та **Smart Constructors**.

## 2. Анатомія проєкту: 5 кроків побудови відмовостійкого конвеєра

### Парадигмальний зсув: Імперативний vs Декларативний стиль

Головна відмінність між підходами полягає в **напрямку інженерного мислення**:

* **Імперативний стиль (Як зробити):** розробник стартує від *початкової точки входу* (`main`, контролер, сирий вхідний потік) і крок за кроком просувається вперед до рішення, вручну керуючи станом процесора (`if`, цикли, мутації `var`).
* **Декларативний стиль (Що отримати):** розробник починає від *бажаного фінального результату* і специфікації контрактів, рухаючись у зворотний бік — до точки входу, зв'язуючи готові декларації в єдиний конвеєр.

| Мова / Технологія | Парадигма | Напрямок мислення | Приклад ментальної моделі |
| :--- | :--- | :--- | :--- |
| **C++** | Імперативна | **Від входу ➔ до результату.** Керуємо пам'яттю та регістрами крок за кроком. | «Створи покажчик, крути `for (size_t i = 0; i < n; ++i)`, мутуй акумулятор, звільни пам'ять». |
| **HTML** | Декларативна | **Від результату ➔ до рушія.** Описуємо цільовий документ, а не команди для GPU. | `<button type="submit">Оплатити</button>` замість інструкцій відеокарті «виділи пікселі [100, 40]». |
| **SQL** | Декларативна | **Від результату ➔ до даних.** Описуємо структуру потрібної вибірки, а не алгоритми пошуку. | `SELECT user_id, SUM(amount) FROM tx WHERE status = 'OK' GROUP BY user_id` замість ручного обходу B-Tree. |
| **Scala (ФП)** | Декларативна | **Від результату ➔ до виклику.** Моделюємо цільові типи та збираємо конвеєр чистих перетворень. | Спочатку декларуємо типи результату (`FinancialReport`, `Transaction`), а конвеєр описуємо як композицію: `parseBatch` ➔ `andThen` ➔ `partitionMap` ➔ `foldLeft`. |

Замість того, щоб писати один монструозний імперативний метод «все в одному» з десятками прапорців і вкладених умов, функціональний конвеєр конструюється **декларативно знизу вгору (Bottom-Up) у 5 послідовних кроків**:

```
[Крок 1: Атоми]       Email, Money, Currency (Smart Constructors у domain.scala)
                            │
                            ▼
[Крок 2: Рядок]       Parser.parseRow: for-comprehension (композиція 4 валідацій)
                            │
                            ▼
[Крок 3: Батч CSV]    Parser.parseBatch: partitionMap (поділ 500k рядків на Left / Right)
                            │
                            ▼
[Крок 4: Бізнес-дії]  Rules.standardPipeline: andThen (комісія + кешбек + нотатки)
                            │
                            ▼
[Крок 5: Фільтр & Підсумок]  Антифрод (partitionMap) ➔ Фінансовий звіт (foldLeft)
```

> 💡 **Примітка щодо назв файлів та класів (Java vs Scala):**  
> Чому `Parser.scala` з великої літери, а `domain.scala` — з маленької?  
> - **Усі класи, типи та енуми — завжди з великої літери (`PascalCase`):** `Email`, `Money`, `Currency`, `Transaction`, `TxError`. Тут немає винятків.  
> - **Файли з великої літери (`Parser.scala`, `Rules.scala`, `Main.scala`):** коли у файлі оголошено один домінантний клас або об'єкт-модуль (`object Parser`), подібно до вимог Java.  
> - **Файли з маленької літери (`domain.scala`, `types.scala`):** усталена Scala-конвенція для файлів-пакетів. У `domain.scala` немає класу `Domain` — це спільний файл для десятка споріднених типів, ADT та смарт-конструкторів.

### Покрокова інженерна еволюція:

1. **Крок 1. Атомарні захисні блоки (Smart Constructors у `domain.scala`):**  
   Ми не парсимо всю транзакцію відразу, поки не вміємо надійно валідувати окремі поля. Створюємо маленькі ізольовані функції `Email.fromString`, `Money.create`, `Currency.fromString`. Кожна з них відповідає за один інваріант і повертає `Either[TxError, T]`.
2. **Крок 2. Збирання рядка через `for`-comprehension (`Parser.scala`):**  
   Маючи надійні атоми, склеюємо їх у залізничну колію для **одного рядка CSV**. Якщо на першому ж кроці (`Email`) стається збій — потяг перемикається на `Left`, а решта полів навіть не парситься (економія тактів процесора).
3. **Крок 3. Пакетна ізоляція збоїв (`Parser.parseBatch`):**  
   Масштабуємо залізницю з одного рядка на весь файл із 500 000 транзакцій. Метод `partitionMap` за один прохід розділяє вхідний потік на два незалежні списки: `List[TxError]` (червона колія помилок) та `List[Transaction]` (зелена колія успіху). Жоден битий рядок не зупиняє систему.
4. **Крок 4. Конвеєр чистих бізнес-правил (`Rules.scala`):**  
   Для транзакцій, які успішно доїхали зеленою колією, налаштовуємо ланцюжок модифікацій. Збираємо кілька чистих функцій `Transaction => Transaction` через `.andThen` (комісія ➔ кешбек ➔ нормалізація опису).
5. **Крок 5. Другий рівень перевірки (Антифрод) та підсумок (`Main.scala`):**  
   Трансформовані транзакції проходять бізнес-перевірку лімітів (`fraudRule`), знову розділяючись через `partitionMap`. Проведені платежі згортаються у фінансовий звіт через `foldLeft` без жодної мутабельної змінної `var`.

## 3. Розбір ключових рішень у коді

### А. Типізовані доменні помилки (Перше знайомство з ADT у `domain.scala`)

> 💡 **Міні-інтуїція: Що таке ADT до [Лекції 04](04_algebraic_data_types.md)?**  
> **ADT (Алгебраїчний тип даних)** тут означає **тип-суму (Sum Type)** — закритий перелік взаємовиключних варіантів («або те, або інше»).  
> У Java звичайний `enum` містить лише плоскі константи (наприклад, `INVALID_EMAIL`). У Scala 3 `enum` дозволяє кожній гілці мати **власні унікальні поля з даними**: номер рядка, причину або ліміт антифроду.  
> Детальну математику та патерни моделювання домену ми розберемо в наступній [Лекції 04](04_algebraic_data_types.md), а зараз сприймайте це як **ідеальний каталог типізованих помилок** для лівої гілки `Left` у залізничному конвеєрі `Either[TxError, A]`.

Замість одного загального винятку `throw new RuntimeException("помилка")` або безликого `String` ми створюємо замкнений перелік можливих збоїв:

```scala
enum TxError:
  case MalformedRow(row: Int, raw: String, expectedCols: Int, actualCols: Int)
  case InvalidEmail(raw: String, reason: String)
  case InvalidAmount(raw: String, reason: String)
  case UnsupportedCurrency(raw: String)
  case FraudLimitExceeded(amount: BigDecimal, limit: BigDecimal)
```

**Чому це дає перевагу у відмовостійкості:**
* **Компілятор на сторожі:** Компілятор точно знає всі варіанти помилок і під час обробки не дозволить «забути» жоден зі збоїв.
* **Повний контекст без здогадок:** `MalformedRow` зберігає точний номер рядка, а `FraudLimitExceeded` — суму та порушений ліміт.
* **Швидкість:** Це легкі об'єкти в купі (heap), які повертаються як звичайні значення без важких нативних викликів `fillInStackTrace()`.

### Б. Розумні конструктори (Smart Constructors)

#### Що робить їх «розумними»?
У традиційному ООП конструктор класу зазвичай публічний і «наївний»: він сліпо приймає будь-яке значення, що в нього передали.

**Розумний конструктор (Smart Constructor)** позбавляє клас наївності двома простими кроками:
1. **Закриває «чорний хід»:** Первинний конструктор позначається як `private`. Виклики `new Email("сміття")` або `Email("сміття")` стають **неможливими на рівні компілятора**.
2. **Єдиний санкціонований вхід:** Створити екземпляр можна виключно через фабричний метод (наприклад, `Email.fromString`), який повертає не «голий» об'єкт, а `Either[TxError.InvalidEmail, Email]`.

```scala
// 1. Конструктор private: неможливо створити об'єкт в обхід валідації
final case class Email private (value: String)

object Email:
  // 2. Єдиний шлях створення: через повернення Either
  def fromString(raw: String): Either[TxError.InvalidEmail, Email] =
    val trimmed = raw.trim
    if !trimmed.contains("@") then
      Left(TxError.InvalidEmail(raw, "Відсутній символ '@'"))
    else
      val parts = trimmed.split("@")
      if parts.length != 2 || parts(0).isEmpty || parts(1).isEmpty then
        Left(TxError.InvalidEmail(raw, "Email повинен мати непорожні ім'я та домен"))
      else if !parts(1).contains(".") then
        Left(TxError.InvalidEmail(raw, "Доменна частина повинна містити крапку"))
      else
        Right(new Email(trimmed.toLowerCase))
```

#### Чому ми робимо так, а не інакше? Порівняння альтернатив

| Підхід | Як виглядає в коді | Чому це катастрофа в продакшені |
| :--- | :--- | :--- |
| **1. Одержимість примітивами (Primitive Obsession)** | `sender: String`, `amount: Double` | Компілятор вважає валідним будь-який текст: `""`, `"не-імейл"` або від'ємний баланс `-100.0`. Якщо сигнатура методу `send(from: String, to: String)`, розробник може легко переплутати порядок аргументів, і компілятор навіть не писне. Доводиться дублювати перевірки в кожному сервісі. |
| **2. Конструктор з винятком (`require`)** | `case class Email(v: String) { require(v.contains("@")) }` | Конструктор кидає `IllegalArgumentException` у рантаймі. Сигнатура методу створення бреше: вона не попереджає про збій. Будь-який виклик треба огортати в `try-catch`, що руйнує чистоту і спалює CPU на створення стек-трейсів. |
| **3. Розумний конструктор (Smart Constructor)** | `Email.fromString(raw): Either[Error, Email]` | **Parse, don't validate!** Якщо у вас у руках є об'єкт типу `Email`, ви на 100% упевнені, що він валідний. Жоден метод у бізнес-логіці чи базі даних більше **ніколи не перевіряє email повторно**. Валідність гарантована самою системою типів. |

### В. Залізничний парсер у `for`-comprehension (`Parser.scala`)

#### Чому саме так?
Ми об'єднуємо кілька незалежних валідацій у плоский, лінійний та декларативний потяг:

```scala
for
  sender    <- Email.fromString(senderRaw)
  recipient <- Email.fromString(recipientRaw)
  currency  <- Currency.fromString(currencyRaw)
  money     <- Money.create(amountRaw, currency)
yield Transaction(
  id = idRaw,
  sender = sender,
  recipient = recipient,
  money = money,
  note = noteOpt // Option[String] замість null!
)
```

#### Що це дає і яка альтернатива?
* **Fail-Fast (Коротке замикання):** Якщо `sender` невалідний, виконання **миттєво зупиняється на першому кроці** і повертає `Left`. Наступні дорожчі перевірки (валідація валюти, конвертація грошей) навіть не викликаються, заощаджуючи такти процесора.
* **Альтернатива 1 — «Піраміда смерті» (Вкладені `if-else`):**
  Без `for-comprehension` довелося б писати 4 рівні сходів: `if (e1.isRight) { if (e2.isRight) { ... } }`. Такий код неможливо читати й розвивати.
* **Альтернатива 2 — Мутабельні прапорці:**
  Заводити змінну `var isValid = true` та накопичувати помилки мутаціями. Це повертає нас до небезпечного змінного стану, який легко ламається в конкурентному середовищі.

### Г. Композиція функцій вищого порядку (`Rules.scala`)

#### Чому бізнес-правило — це функція `Transaction => Transaction`?
Замість того, щоб змішувати всі бізнес-правила (комісії, кешбеки, нормалізацію тексту) в один гігантський монолітний метод `processTransaction`, ми виділяємо кожне правило в **ізольовану чисту функцію**:

```scala
type Transformer = Transaction => Transaction

val applyProcessingFee: Transformer = tx => tx.copy(fee = BigDecimal(5.00))
val applyVipCashback: Transformer   = tx => /* нарахування 2% для суми >= 1000 */
val normalizeNote: Transformer      = tx => tx.copy(note = tx.note.map(_.capitalize))

// Склеювання конвеєра в один вираз через andThen:
val standardPipeline: Transformer =
  applyProcessingFee
    .andThen(applyVipCashback)
    .andThen(normalizeNote)
```

#### Порівняння архітектурних підходів:
* **Принцип відкритості/закритості (Open-Closed Principle):** Потрібно додати святкову акцію чи змінити комісію для юридичних осіб? Ви просто пишете ще одну чисту функцію і додаєте її в ланцюжок `andThen` або передаєте список функцій у `foldLeft`. Жоден старий рядок коду не модифікується, а отже, не ризикує зламатися.
* **Ізольоване тестування без моків:** Кожне правило тестується окремим юніт-тестом на 3 рядки: передав `Transaction`, перевірив `result.fee`. Жодних важких баз даних чи підняття сервісних контейнерів.
* **Альтернатива (ООП-моноліт зі змінами стану):**
  Метод `void applyRules(Transaction tx)` на 300 рядків із мутаціями `tx.setFee(...)`. Будь-яка зміна порядку викликів призводить до прихованих сайд-ефектів: наприклад, кешбек випадково розраховується від суми вже після списання комісії.

### Д. Відмовостійна пакетна обробка через `partitionMap`

#### Чому батч не повинен «падати» від одного битого рядка?
У реальних фінтех-системах щоночі надходять клірингові виписки на 500 000 операцій. Якщо на 499 999-му рядку трапився битий email, система не має права перервати весь імпорт і заблокувати пів мільйона платежів клієнтів!

Метод `partitionMap` у поєднанні з `zipWithIndex` вирішує цю проблему елегантно та ефективно:

```scala
// Реалізація в Parser.scala:
def parseBatch(lines: List[String]): (List[TxError], List[Transaction]) =
  lines.zipWithIndex.partitionMap { case (line, idx) =>
    parseLine(idx + 1, line) // нумерація рядків з 1 для зручності аудиту
  }
```

> 💡 **Що робить `zipWithIndex`:**  
> Метод «зчіплює» (як застібка-блискавка *zipper*) кожен елемент списку з його індексом: `List("a", "b").zipWithIndex` ➔ `List(("a", 0), ("b", 1))`.  
> Це чиста заміна імперативному лічильнику `for (int i = 0...)`: жодних мутабельних змінних `var` та нульовий ризик виходу за межі масиву (`IndexOutOfBoundsException`).

#### Чому саме `partitionMap`, а не інші способи:
* **Ефективність $O(N)$ в один прохід:** Традиційний підхід `list.filter(_.isLeft)` та `list.filter(_.isRight)` змушує JVM проходити по пам'яті двічі й створювати проміжні колекції. `partitionMap` робить це за один прохід і одразу витягує чисті значення з контейнерів (`Left(err) => err`, `Right(tx) => tx`).
* **Повна ізоляція невдач:** Усі 99% валідних транзакцій негайно передаються далі на фінансовий процесинг. Усі 1% збоїв збираються в типізований реєстр `List[TxError]` для аудиту або відповіді клієнту.
* **Альтернатива (Імперативний цикл із буферами):**
  Створення порожніх списків `val errors = new ArrayList()`, заповнення їх у циклі через `try-catch`. Це багатослівно, створює змінний стан і легко призводить до гонитви станів (Race Condition) при паралельній обробці.

## Резюме

* **Винятки лише для катастроф:** `throw Exception` — лише для непередбачуваних системних збоїв (падіння диска, OOM). Бізнес-помилки валідації моделюються через `Either`.
* **Smart Constructor:** Ховайте первинний конструктор (`private`), щоб не пропустити некоректні дані в домен.
* **Композиція замість моноліту:** Розбивайте складну обробку на ланцюжок чистих функцій (`andThen` / `foldLeft`).

## Контрольні питання для самоперевірки

<details markdown="1">
<summary>1. Що станеться, якщо у for-comprehension над Either перший крок поверне Left, а другий викликає важку мережеву операцію?</summary>

Другий крок навіть не буде викликаний! За правилами монадичного зв'язування `flatMap`, як тільки генератор зустрічає `Left`, він миттєво повертає цей `Left` як результат усього виразу. Це захищає систему від марних обчислень.
</details>

<details markdown="1">
<summary>2. Чому copy у case class є ключовим інструментом для побудови конвеєрів трансформації?</summary>

Тому що `copy` повертає **новий незмінний об'єкт**, змінюючи лише вказані поля (наприклад, `tx.copy(fee = 5.0)`), зберігаючи всі інші поля незмінними за принципом Structural Sharing без мутації оригінального об'єкта.
</details>

<details markdown="1">
<summary>3. Чому метод partitionMap надійніший за поєднання двох викликів filter?</summary>

Виклик `filter` двічі (`list.filter(_.isLeft)` та `list.filter(_.isRight)`) проходить по всій колекції двічі (два проходи по пам'яті). `partitionMap` робить розділення **за один прохід** і одночасно розгортає значення з контейнерів (`Left(e) => e`, `Right(v) => v`), повертаючи готовий кортеж `(List[E], List[A])`.
</details>
