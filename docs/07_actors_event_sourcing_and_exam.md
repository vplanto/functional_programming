## Питання для розминки

<details>
<summary>1. Чому акторам у моделі конкурентності взагалі не потрібні блокування (Locks / Mutex / synchronized)?</summary>

Тому що кожен актор має свою особисту поштову скриньку (Mailbox). Повідомлення з черги вичитуються і обробляються актором **суворо послідовно в один потік**. Внутрішній стан актора ізольований: жоден зовнішній потік не може доторкнутися до його пам'яті напряму, що математично унеможливлює стан гонитви (Race Condition).
</details>

<details>
<summary>2. Що означає знаменитий принцип відмовостійкості систем на акторах: «Let It Crash» (Хай впаде)?</summary>

Замість того, щоб засмічувати кожен рядок бізнес-коду параноїдальними `try/catch` з непередбачуваним станом після збою, розробник дозволяє актору впасти. Актор-батько (Супервізор) спостерігає за падінням і автоматично застосовує чисту стратегію зцілення (наприклад, перезапускає актора з чистим початковим станом).
</details>

<details>
<summary>3. У чому різниця між традиційним збереженням стану в реляційній базі та парадигмою Event Sourcing?</summary>

Традиційна БД виконує `UPDATE accounts SET balance = 500`, безповоротно стираючи історію того, як цей баланс виник. Парадигма **Event Sourcing** нічого не перезаписує — вона лише додає незмінні факти в лог (`Поповнення +1000`, `Списання -300`, `Комісія -200`). Поточний стан рахунку — це звичайна функціональна згортка (**`foldLeft`**) над цим логом подій.
</details>

## 1. Архітектурний кейс: «Смерть квиткового шлюзу на замках БД проти неблокуючого Актора»

**Контекст:** Онлайн-каса продає останні 100 VIP-квитків на фінал Ліги Чемпіонів.  
Рівно о 10:00 сайт відкриває продаж. 50 000 фанатів одночасно тиснуть «Купити квиток».

```
50 000 клієнтів ──► [ 100 потоків бекенду ] ──► [ PostgreSQL: UPDATE tickets SET buyer = ... ]
                    (Кожен хапає рядок у транзакції SELECT ... FOR UPDATE)
```

### Що пішло не так в ООП-підході (Pessimistic Locks):
1. Сотні потоків одночасно спробували заблокувати один і той самий рядок у базі через `SELECT ... FOR UPDATE`.
2. База даних захлинулася в арбітражі взаємних блокувань (Deadlock Detection). Навантаження на CPU бази підскочило до 100%, хоча корисна робота не виконувалася.
3. Пул з'єднань сервера вичерпався за 3 секунди, сервери впали, а фанати отримали білий екран HTTP 500.

### Як цю задачу вирішує один-єдиний Актор (Apache Pekko / Akka):
Замість тисяч потоків, що б'ються за пам'ять, ми створюємо **одного актора `TicketDispenser`**:

```
50 000 запитів ──► [ Mailbox: незмінні повідомлення BuyTicket ] ──► [ Актор TicketDispenser ]
                   (Чекають у швидкій черзі в пам'яті RAM)            (Обробляє 1-потоково)
```
1. Актор тримає лічильник `ticketsLeft = 100` у локальній пам'яті.
2. 50 000 повідомлень миттєво падають у його поштову скриньку без жодних локів.
3. Актор вичитує їх зі швидкістю **5 000 000 повідомлень на секунду** (суто процесорні інструкції без I/O).
4. Перші 100 повідомлень отримують відповідь `Right(Ticket)`, решта 49 900 повідомлень за лічені мілісекунди отримують чисту відповідь `Left("SoldOut")`.
5. База даних навіть не відчула навантаження!

## 2. Модель Акторів: Анатомія та 3 закони Г'юїта (1973)

Актор — це фундаментальний примітив конкурентних обчислень (як об'єкт в ООП, але з ізольованою пам'яттю та асинхронною поштою):

```
                     ┌────────────────────────────────────────────────────────┐
                     │                         АКТОР                          │
                     │                                                        │
Повідомлення         │  ┌───────────────────────┐   ┌──────────────────────┐  │
(case-класи) ───────►│  │ Mailbox (Пошта)       │──►│ Поведінка (Behavior) │  │
                     │  │ [msg1] [msg2] [msg3]  │   │ Обробляє msg по черзі│  │
                     │  └───────────────────────┘   └──────────┬───────────┘  │
                     │                                         │              │
                     │  Ізольований стан (State) ◄─────────────┘              │
                     └────────────────────────────────────────────────────────┘
```

### 3 закони Карла Г'юїта:
Отримавши повідомлення, актор може зробити лише три речі:
1. **Надіслати** скінченне число повідомлень іншим акторам (асинхронно через оператор `!`).
2. **Створити** скінченне число дочірніх акторів (`context.spawn`).
3. **Визначити поведінку** для обробки наступного повідомлення (стати чистою функцією наступного кроку).

### Ідіоматичний актор на Scala 3 (Apache Pekko Typed):

```scala
import org.apache.pekko.actor.typed.Behavior
import org.apache.pekko.actor.typed.scaladsl.Behaviors

// 1. Повідомлення — це закритий ADT (Лекція 04):
enum CounterCommand:
  case Increment
  case GetValue(replyTo: org.apache.pekko.actor.typed.ActorRef[Int])

// 2. Актор як чиста функція, що повертає нову поведінку:
object CounterActor:
  def apply(currentCount: Int = 0): Behavior[CounterCommand] =
    Behaviors.receiveMessage {
      case CounterCommand.Increment =>
        // Переходимо в новий стан БЕЗ жодного var чи мутації!
        CounterActor(currentCount + 1)

      case CounterCommand.GetValue(replyTo) =>
        replyTo ! currentCount // Відправляємо відповідь поштою
        Behaviors.same         // Лишаємося в тому самому стані
    }
```
Зверніть увагу: **тут немає жодного `var`!** Перехід стану — це звичайний рекурсивний виклик із новим аргументом.

#### 📬 Паттерн `replyTo`: Чому актори повертають `Unit` і як отримати відповідь?
Студенти часто запитують: *«Чому в методі GetValue ми не пишемо return currentCount?»*
* **Актори спілкуються суворо асинхронно:** Метод обробки повідомлень повертає не дані, а наступну поведінку (`Behavior`).
* **Конверт зі зворотною адресою:** Єдиний спосіб отримати відповідь — передати адресу відправника прямо всередині самого запиту: `case GetValue(replyTo: ActorRef[Int])`.
* Актор бере цей канал і відправляє результат окремим асинхронним листом: `replyTo ! currentCount`.

## 3. Філософія стійкості: «Let It Crash» та Ієрархія нагляду

В імперативних системах помилки часто призводять до витоку пам'яті чи зависання потоків.  
В екосистемі акторів діє закон: **той, хто виконує роботу, не повинен займатися лікуванням своїх помилок**.

```
                           ┌────────────────────────┐
                           │   Актор-Супервізор     │
                           │   (Батьківський вузол) │
                           └───────────┬────────────┘
                                       │
                         Спостерігає за дочірніми:
                                       │
                      ┌────────────────┴────────────────┐
                      ▼                                 ▼
             [ Воркер-Парсер ]                [ Воркер-Мережа ]
             (Падає з помилкою!)              (Працює штатно)
```

### 🛡️ Демістифікація «Let It Crash» на рівні JVM-потоків: Чому програма не гине?
У класичній Java, якщо системний потік кидає необроблений `RuntimeException`, він аварійно гине.  
Чому ж у Pekko/Akka падіння актора не вбиває ні застосунок, ні пул потоків?

* **Перехоплення на рівні Dispatcher:**  
  Внутрішній диспетчер Akka/Pekko обгортає виклик кожного актора у системний перехоплювач.
* **Збереження потоку ОС:**  
  Коли актор падає з винятком, робочий потік із пулу **не помирає** — він просто повертається в пул і негайно береться виконувати завдання інших акторів.
* **Безпечна маршрутизація:**  
  Сам виняток безпечно запаковується в службове системне повідомлення і передається батьківському актору-супервізору для прийняття рішення.

### 4 стратегії супервізора (Supervision Strategies):
Коли воркер падає з критичним винятком, супервізор вирішує його долю:
1. **`Restart` (Перезапуск):** Створити новий екземпляр воркера з чистим початковим станом, зберігши всі невідпрацьовані листи в Mailbox.
2. **`Resume` (Продовжити):** Проігнорувати помилку й перейти до наступного листа в черзі.
3. **`Stop` (Зупинити):** Вбити актора назавжди.
4. **`Escalate` (Ескалювати):** Якщо батько сам не знає, що робити — впасти і передати проблему дідусю (головному супервізору).

## 4. Архітектура рушія `23_runner`: Патерн «Functional Core, Imperative Shell» та детермінований Event Log

Коли ви відкриваєте вихідний код [Engine.scala](file:///home/pvv/projects/onu/functional_programming/23_runner/src/main/scala/runner/Engine.scala), ви бачите не акторів і не реактивні стріми, а покроковий цикл симуляції:
```scala
while hero.alive && tick < maxTicks && !reachedStopSpeed do
  ...
  hero = hero.copy(...)
```
У студента виникає справедливе запитання: *«Чому в курсі з функціонального програмування в центрі рушія стоїть цикл `while` та мутабельні змінні `var hero`, `var tick`?»*

Це не помилка і не "зрада ідеалів ФП". Це класичний патерн сучасного софтверного інжинірингу: **«Функціональне ядро, імперативна оболонка» (Functional Core, Imperative Shell)**.

### 1. Functional Core (Чисте функціональне ядро)
Уся бізнес-логіка гри, фізика перешкод і прийняття рішень є **на 100% незмінними (immutable) та математично чистими**:
* **Дані як факти:** `HeroState`, `TunnelSlice`, `Observation`, `TickRecord` — це чисті `case class` та `enum`.
* **Інтерфейси ботів:** `CyberBot.decide(obs: Observation): Action` — чиста функція. Бот не знає про файли чи консоль; він приймає незмінний знімок тунелю і повертає команду `Action`.
* **Детермінізм:** За однакового сіда тунелю та алгоритму бота симуляція дає біт-в-біт ідентичний результат на будь-якому комп'ютері.

### 2. Imperative Shell (Імперативна оболонка `Engine`)
Зовнішній світ програми не є чистим: там є взаємодія з ОС, таймери, файловий I/O, вивід у консоль і загроза нескінченних циклів у коді студентів.  
Клас `Engine` бере на себе цю «брудну» роботу:
* **Ізольований стан:** Змінні `var hero` та `var tick` замкнені виключно всередині методу `run()`. Мутабельність **суворо ізольована** й ніколи не просочується назовні в публічні інтерфейси ботів.
* **Гранична швидкодія JVM (Zero-GC):** У режимі бенчмарку тунель симулюється зі швидкістю **1 мкс / тік**. Створення нових структур на рівні циклу перевантажило б збирач сміття (GC). Локальний `while` забезпечує максимальну продуктивність JVM.
* **Асинхронний сторож:** Виклик бота ізольовано у `Future(bot.decide(observation))(botExecutionContext)` з жорстким таймаутом `budgetNanos`. Якщо алгоритм студента зависне у `while(true)`, рушій не заблокується, а зафіксує таймаут.

### 3. Детермінований Event Log (Історія як послідовність фактів)
Незважаючи на локальний `while`, результат гри фіксується як **незмінний журнал подій (Event Log)**:
* На кожному кроці рушій генерує незмінний запис `TickRecord`:
  ```scala
  TickRecord(tick, heroBefore, action, heroAfter, responseTimeNanos, slice)
  ```
* Забіг зберігається як список фактів `history: List[TickRecord]`.
* Завдяки цьому ми експортуємо забіг у компактний JSON ([JsonExporter.scala](file:///home/pvv/projects/onu/functional_programming/23_runner/src/main/scala/runner/JsonExporter.scala)) і відтворюємо візуальний реплей у браузері (`docs/viewer/index.html`) без збереження важких дампів пам'яті.

### 4.1. Модель Акторів Pekko/Akka: Як масштабувати рушій до розподіленого мультиплеєра

Чому в однокористувацькому `23_runner` немає акторів прямо зараз? Тому що для локальної однопотокової гри актори створили б непотрібний оверхед черг і диспетчеризації.  
Але щойно ми масштабуємо гру до **Cyber Tunnel Arena (розподілений мультиплеєр на тисячі гравців)**, модель Акторів стає незамінною:

```
[ Гравець 1 (WebSocket) ] ──► [ Актор PlayerSession 1 ] ──┐
                                                          ├──► [ Актор GameRoom (Engine) ]
[ Гравець 2 (WebSocket) ] ──► [ Актор PlayerSession 2 ] ──┘     (Крутить спільний тунель без блокувань!)
```

1. **Ізоляція збоїв (Let It Crash):** Кожен гравець обслуговується окремим актором. Якщо бот одного гравця впаде через OutOfMemoryError, впаде лише цей актор, а не весь ігровий сервер.
2. **Арбітраж без м'ютексів:** Актор кімнати `GameRoomActor` приймає рішення гравців через свою поштову скриньку (`Mailbox`), обробляє їх послідовно в один потік і розсилає оновлений стан тунелю.
3. **Горизонтальне масштабування (Pekko Cluster):** Тисячі ігрових кімнат можна розподілити по кластеру серверів без спільних блокувань пам'яті.

## 5. Архітектурний путівник до іспиту (Як захищати свій код)

Коли викладач або Principal Architect запитає вас на іспиті: *«Чому ви написали саме так?»*, у вас має бути залізна відповідь інженера, а не студента-початківця:

| Імперативний антипатерн (Junior) | Функціонально-реактивна норма (Senior) | Чому саме так (Ваша відповідь на іспиті) |
| :--- | :--- | :--- |
| `var x = 10` | `val x = 10` | Незмінність унеможливлює Race Conditions і дозволяє масштабувати код на всі ядра CPU без блокувань. |
| `String s = null` | `Option[String]` | Компілятор гарантує відсутність `NullPointerException` ще до запуску коду в продакшн. |
| `throw new Exception()` | `Either[DomainError, T]` | Винятки спалюють CPU на збиранні стек-трейсів (`fillInStackTrace`). `Either` швидший у 60 разів (Практика 03). |
| `class Order { String status; }` | ADT (`enum Order: Pending, Shipped`) | Make Illegal States Unrepresentable: компілятор не дозволить трекінг-номеру існувати в скасованому замовленні (Лекція 04). |
| `case _ => "Unknown"` | Явний перелік усіх гілок у `match` | Захист від втрати нових статусів при рефакторингу (Exhaustiveness checking компілятора). |
| Блокуючий `Thread.sleep` або JDBC у глобальному пулі | Виділений `ExecutionContext` або Non-blocking I/O | Блокування 4 потоків у Netty Event Loop паралізує сервер для всіх 10 000 клієнтів (Лекція 06). |
| Перезапис стану `balance = balance + x` | Event Sourcing (`foldLeft` над подіями) | Незмінний аудит-лог фактів дає можливість у будь-яку мить відтворити історію системи та спрощує реплікацію. |
| Глобальний змінний стан у бізнес-коді | Functional Core, Imperative Shell | Мутабельність суворо ізольована у зовнішній оболонці (Engine), а бізнес-ядро і боти залишаються 100% чистими й детермінованими. |

## Резюме курсу: Правило трьох секунд

* **Відсутність змінного стану = масштабування без болю:** Безстановость (Statelessness) дозволяє запускати тисячі мікросервісів у хмарі без конфліктів за пам'ять.
* **Система типів — ваш безкоштовний тестувальник:** Інвестуйте час у дизайн ADT, і компілятор відсіче 90% багів до рантайму.
* **Асинхронність потребує дисципліни:** Пам'ятайте про ціну реактивного траблшутингу, захищайте потік від блокувань і використовуйте Backpressure.

</details>

<details>
<summary>2. Чому в розподілених системах архітектура Event Sourcing ідеально підходить для мікросервісів?</summary>

Події — це доконані факти минулого (`OrderCreated`, `PaymentReceived`), які ніколи не змінюються. Їх можна безпечно реплікувати через брокери (Kafka) до будь-якої кількості незалежних сервісів без блокувань центральної бази даних.
</details>

<details>
<summary>3. Яке головне запитання ставить собі розробник перед тим, як написати функцію у чистому ФП?</summary>

«Чи є ця функція детермінованою (завжди однаковий вихід на однаковий вхід) і чи не має вона прихованих побічних ефектів (Side Effects), які змінюють світ за межами її аргументів?». Якщо так — функція на 100% потокобезпечна, масштабована та легко тестується.
</details>
