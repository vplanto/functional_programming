Але головна складність полягає саме у ручному розбитті масиву на рівні шматки (чанкі) та правильній фінальній агрегації результатів з різних потоків. Усе це — десятки рядків коду, де дуже легко зловити стан гонитви або забути про синхронізацію.
   </details>

2. **Що станеться, якщо спробувати зробити велику колекцію незмінною (immutable) "в лоб" у класичній Java або C++, не маючи під капотом спеціальної архітектури?**
   <details markdown="1">
   <summary>Відповідь</summary>
   
   Ви отримаєте катастрофічне падіння продуктивності. Якщо для кожної зміни елемента вам доведеться повністю дублювати весь масив на мільйон записів у нову область пам'яті (щоб уникнути мутацій), програма миттєво вичерпає оперативну пам'ять (OOM) і витратить весь процесорний час на роботу з Garbage Collector-ом або на копіювання байтів. Саме тому справжнє ФП використовує структурне перевикористання (Structural Sharing).
   </details>

У першій лекції ми розібрали, що незмінний стан (Immutability) та чисті функції (Pure Functions) дозволяють вирішити більшість проблем багатопоточності (дедлоки, стан гонитви). У цьому воркшопі ми побачимо це на практиці.

## Експрес-курс: Синтаксис Scala перед стартом

> **Довідник:** усі базові шаблони зібрані в [p01. Шаблони Scala](p01_scala_templates.md) — туди звертайтесь, коли забули синтаксис. Нижче — мінімум саме для цієї практики.

Оскільки це наша перша практика, давайте розберемо базові конструкції мови Scala, які ми зустрінемо в коді.

### 1. Структура мінімальної програми
У Java або C++ точкою входу є статичний метод `main` всередині класу. У Scala ми використовуємо **синглтон-об'єкт** (ключове слово `object`). Якщо він розширює (`extends`) базовий трейт `App`, то весь код безпосередньо всередині нього автоматично стає точкою входу в програму:

```scala
object MyFirstProgram extends App {
  // Ваш код пишеться прямо тут
}
```

### 2. Змінні: `val` проти `var` та виведення типів
Функціональне програмування базується на незмінності (Immutability). Тому в Scala є два принципово різних типи змінних:
- `val` (Value) — **незмінна константа**. 99% вашого коду складатиметься з `val`. Перезаписати її значення неможливо.
- `var` (Variable) — **мутуюча змінна** (як класичні змінні в С++). Її використання зведене до мінімуму (переважно лише всередині локальних функцій для мікрооптимізацій).

> **Важливо про типи:** Scala є **строго статично типізованою** мовою (як Java або C++). Але зверніть увагу: ми ніде не вказуємо тип даних вручну (не пишемо `double pi = 3.14`). Це тому, що компілятор Scala має потужний механізм **виведення типів (Type Inference)**. Він сам бачить значення і підставляє правильний тип під капотом, роблячи код дуже лаконічним без втрати надійності.

```scala
val pi = 3.14 // Константа, ідеально підходить для багатопоточності (компілятор сам зрозумів, що це Double)
var counter = 0 // Змінна (намагаємося уникати в архітектурі)
```

### 3. Магія конвеєрів (Pipeline)
У ФП ми рідко використовуємо класичні імперативні цикли `for` для обробки масивів. Натомість ми будуємо "конвеєри". Вихід однієї функції миттєво стає входом для наступної, утворюючи ланцюжок викликів:

```scala
val result = (1 to 100)        // 1. Генеруємо числа від 1 до 100 (де "to" — це теж функція!)
  .map(x => x * 2)             // 2. Множимо кожне число на 2 (лямбда-вираз)
  .sum                         // 3. Одразу знаходимо суму всіх елементів
```
Цей код читається як звичайна англійська мова і не потребує створення проміжних порожніх масивів.

> **Як працює `to`?** Запис `1 to 100` — це синтаксичний цукор (Infix notation). Насправді це виклик методу на об'єкті (числі 1). У Scala будь-який метод з одним параметром можна викликати без крапки та дужок. Формальний (класичний) запис цього ж коду виглядає так: `1.to(100)`.

> **Про лямбди:** Вираз `x => x * 2` — це анонімна функція (лямбда). Для початківців ми явно називаємо параметр `x`, щоб було зрозуміло, що відбувається. Але в ідіоматичній Scala цей самий запис можна скоротити ще більше за допомогою "магічного" підкреслення: `.map(_ * 2)`.

### 4. Ввід/Вивід та I/O
Вивід тексту в консоль працює через звичайний `println("Текст")`. Проте згадаймо лекцію: будь-який вивід на екран — це **побічний ефект (side effect)**. У справжніх ФП-системах чисті функції ніколи не містять `println`. Ми робимо це лише на самому "краю" програми (в так званому Imperative Shell).

> **А як тоді дебажити чисті функції?**
> Часто виникає питання: "Якщо не можна писати логи чи `println` всередині функції, як зрозуміти, що там відбувається?".
> 1. **Unit-тести замість логів:** Чиста функція завжди повертає однаковий результат для однакових вхідних даних. Її не треба дебажити "в бою" — ви просто пишете простий Unit-тест, який перевіряє конкретну логіку в ізоляції.
> 2. **Логи як дані:** Якщо бізнес-логіці критично потрібно збирати аудит-логи, чиста функція не *друкує* їх на екран. Вона просто *повертає* їх як звичайний текст разом із результатом обчислень (наприклад, у вигляді об'єкта `(Result, List[LogMessage])`). А вже зовнішній шар (Imperative Shell) бере цей список і фізично пише його у файл чи консоль.

## Постановка завдання: Оптимізація Fraud Detection системи

**Контекст:** Ви працюєте Data-інженером у фінтех-стартапі. Ваша система щодня обробляє мільйон банківських транзакцій, аналізуючи кожну на наявність шахрайства (Fraud Detection). Перевірка однієї транзакції вимагає складних математичних обчислень. 

**Проблема:** Бізнес скаржиться, що обробка транзакцій займає занадто багато часу. Ваші сервери мають багато потужних ядер, але поточний код написаний послідовно і використовує лише одне ядро, ігноруючи решту апаратних ресурсів.

**Ваша задача:**
1. Відкрити проєкт `01_parallelism` та ознайомитися з файлом `src/main/scala/Main.scala`. Ви побачите симуляцію історії на 1 000 000 транзакцій та важку функцію `analyzeTransactionRisk`.
2. Запустити поточний (послідовний) код через термінал і зафіксувати, скільки часу займає обробка на вашій машині:
   ```bash
   sbt run
   ```
3. Розпаралелити обробку! Проаналізуйте код нижче у файлі (з викликом `data.par.map(...)`) і переконайтеся на власні очі, як **додавання всього одного слова (`.par`)** змушує всі ядра вашого процесора працювати на повну потужність. Зверніть увагу на показник прискорення.

## Що тут відбувається?

Коли ми викликаємо звичайний `.map(...)` на колекції, програма обчислює елементи строго послідовно, в один потік (Single Thread). 
*(Примітка: якщо ви відкриєте диспетчер задач, ви можете побачити, що навантаження "стрибає" між різними ядрами. Це операційна система (OS Scheduler) перекидає єдиний потік з ядра на ядро. Робиться це для уникнення локального перегріву (hotspots) конкретної ділянки кристала, щоб процесор міг довше тримати високі частоти Turbo Boost. Але є й мінус: при кожному такому стрибку потік втрачає свій "гарячий" локальний кеш L1/L2 на старому ядрі і змушений підтягувати дані з повільнішого L3 або RAM).*
Оскільки завдання штучно ускладнене, обробка мільйона елементів займає близько 25 секунд.

Додавання `.par` (від слова *parallel*) під капотом перетворює наш стандартний `Vector` на `ParVector`. Тепер метод `map` розбиває мільйон елементів на дрібні шматки (чанкі) і віддає їх усім доступним ядрам вашого процесора одночасно. Після того, як кожне ядро обробило свій шматок, результати агрегуються (завдяки виклику `.sum`).

### Чому це безпечно?
Тому що функція `analyzeTransactionRisk` є **чистою (pure)**, а масив транзакцій `data` — **незмінним (immutable)**. Жоден потік не намагається мутувати дані іншого потоку, тому нам взагалі не потрібні м'ютекси (Mutex), блокування (Locks) і ми гарантовано не зловимо Deadlock.

Паралельне програмування, яке в С++ вимагало б десятків рядків складного коду з `std::thread`, у Функціональному програмуванні зводиться до магії одного слова — `.par`.

> **Зверніть увагу:** Прискорення не буде ідеально пропорційним кількості ядер (наприклад, на 8 ядрах програма не працюватиме рівно у 8 разів швидше). Частина часу завжди витрачається на організацію пулу потоків, розбиття даних та фінальну агрегацію результатів (Закон Амдала). Проте різниця між одним ядром та всіма все одно вражає.

3. Зверніть увагу, що результат **завжди різний** (і хибний). Це класичний стан гонитви (Race Condition) — найгірший нічний жах імперативних розробників.

### Завдання 2: Рефакторинг у чисте ФП

> **📚 Що потрібно знати для виконання:**
> 1. Теоретична база: чому ми відмовляємося від `var` і що таке чисті функції — читайте у [Лекції 01: Основи ФП](01_immutability_and_state.md).
> 2. Як працює синтаксис `match` у Scala: [Офіційна документація по Pattern Matching](https://docs.scala-lang.org/tour/pattern-matching.html).
> 3. Як працюють колекції (`filter`, `map`): [Офіційна документація по Collections API](https://docs.scala-lang.org/scala3/book/collections-methods.html).

Досить використовувати імперативний підхід з `var`. Напишіть чистий код, де все є виразом (Expression-Oriented Programming).
1. У файлі `Workshop.scala` є заготовки для Алгебраїчних Типів Даних (ADT) `RiskLevel`.
2. Реалізуйте чисту функцію `categorize`, використовуючи **Pattern Matching** (`match`). Ніяких `if-else` чи присвоювань змінних!
3. Реалізуйте чисту функцію `getMultiplier` так само через `match`.
4. Напишіть чистий конвеєр (`.filter(...).map(...).sum`), який спочатку фільтрує транзакції, а потім застосовує до них ваші функції.

## Troubleshooting (Вирішення проблем)
- **`sbt` не знайдено:** Переконайтеся, що ви встановили Scala та sbt (найкраще через [Coursier](https://get-coursier.io/)).
- **Помилка `not found: value par`:** Починаючи зі Scala 2.13, паралельні колекції винесені в окрему бібліотеку. Переконайтеся, що вгорі файлу є `import scala.collection.parallel.CollectionConverters._`, а у файлі `build.sbt` підключена відповідна бібліотека.
- **Як запустити конкретний файл?** Якщо в проєкті кілька точок входу (кілька `object ... extends App`), використовуйте `sbt "runMain НазваОбєкта"`, наприклад: `sbt "runMain Workshop"`.

<details markdown="1">
<summary>Спойлер: Референсне рішення (Завдання 2)</summary>

```scala
def categorize(amount: Double): RiskLevel = amount match {
  case a if a > 80.0 => HighRisk
  case a if a > 50.0 => MediumRisk
  case _             => LowRisk
}

def getMultiplier(level: RiskLevel): Double = level match {
  case HighRisk   => 1.5
  case MediumRisk => 1.2
  case LowRisk    => 1.0
}

val finalRiskSum = data.par
  .filter(_ > 50.0)
  .map(t => t * getMultiplier(categorize(t)))
  .sum
```
</details>
