## Питання для розминки

<details markdown="1">
<summary>1. Чому цикл `for` — найнебезпечніше місце для прихованих багів в інженерному коді?</summary>

Цикл `for (int i = 0; i < n; i++)` вимагає керування трьома речами одночасно: початковим індексом, кроком ітерації (інкрементом) та умовою виходу. Помилка на одиницю (**Off-by-one bug**), випадкова зміна лічильника всередині тіла або вихід за межі пам'яті трапляються щодня. Функціональний конвеєр оперує колекцією як цілісним значенням — там **фізично немає індексів**, тому такий клас багів унеможливлений на рівні дизайну мови.
</details>

<details markdown="1">
<summary>2. Що спільного між промисловим конвеєром заводу та функціональним кодом?</summary>

На сучасному автозаводі робітники та роботи-зварювальники стоять нерухомо на своїх місцях. Конвеєрна стрічка рухає **незмінні деталі крізь нерухомі інструменти**. У ФП функції — це зафіксовані інструменти, а дані протікають крізь них без побічних змін навколишнього середовища.
</details>

<details markdown="1">
<summary>3. Що означає термін «функція як громадянин першого класу» (First-Class Citizen)?</summary>

Це означає, що функція позбавлена статусу "другорядного службового коду". Вона стає **таким самим звичайним значенням**, як число `42` чи рядок `"Hello"`: її можна присвоїти змінній, покласти в масив, передати аргументом в інший метод або повернути як результат обчислень.
</details>

## 1. Архітектурний кейс: Тиха катастрофа на Чорну п'ятницю

**Контекст:** Великий маркетплейс обробляє пікове святкове навантаження (15 000 замовлень на хвилину).  
Бекенд написаний класичним імперативним стилем. Щоб тимчасовий збій однієї картки не блокував обробку всього батчу замовлень, розробник реалізував списання та розсилку квитанцій:

```java
List<PaymentReceipt> receipts = new ArrayList<>();

// 1. Списання коштів
for (Order order : batch) {
    try {
        PaymentReceipt receipt = paymentGateway.charge(order);
        receipts.add(receipt);
    } catch (PaymentException e) {
        log.warn("Payment failed for order: " + order.getId());
    }
}

// 2. Розсилка квитанцій покупцям
for (int i = 0; i < receipts.size(); i++) {
    emailService.sendReceipt(batch.get(i).getEmail(), receipts.get(i));
}
```

### Поведінка на тестах:
Юніт-тести з моками пройшли бездоганно: платіжний шлюз у тестовому середовищі успішно підтверджував транзакції, квитанції відправлялися покупцям, CI/CD показав 100% зелених тестів. Код задеплоїли в продакшен.

<details markdown="1">
<summary>Що пішло не так у продакшені?</summary>

1. Під реальним навантаженням у частини покупців банки відхилили транзакції через нульовий баланс чи ліміти (`PaymentException`).
2. Блок `catch` сумлінно перехопив винятки та залогував `warn`. Проте для збійного замовлення квитанція до списку `receipts` не додалася.
3. Довжина `receipts` стала меншою за `batch` — відбувся **непомітний зсув індексів**.
4. У другому циклі `batch.get(i).getEmail()` та `receipts.get(i)` звернулися до **різних людей**:
   - Покупець із відхиленою оплатою несподівано отримав квитанцію наступного клієнта.
   - Усі наступні сотні покупців у батчі отримали **чужі платіжні чеки** з чужими сумами, прізвищами та адресами доставки.
5. Результат: масовий витік персональних даних (GDPR breach) та репутаційний колапс. При цьому **жоден мікросервіс не впав, HTTP-статус залишався 200 OK, а моніторинг мовчав**.
</details>

### Як це розв'язується у функціональному стилі:

Замість двох незалежних мутабельних списків та крихких індексів ми будуємо **декларативний конвеєр трансформації**. Помилка списання більше не поглинається в блоці `catch`, а стає явним типізованим значенням — `Either[PaymentError, PaymentReceipt]`.

**До чого тут атомарність?**  
В імперативному коді замовлення та чек існували роздільно: зв'язок між ними тримався лише на сліпій вірі, що `batch.get(i)` відповідає `receipts.get(i)`. У функціональному стилі ми об'єднуємо замовлення та результат його списання в **нероздільну (атомарну) пару** `(Order, Either[...])`. Вони створюються одночасно й рухаються системою як єдине ціле: навіть якщо половина платежів упаде, результат гарантовано залишається прикріпленим до свого власника.

```scala
// ✅ Функціональний підхід: атомарний зв'язок замовлення та результату
val processed: List[(Order, Either[PaymentError, PaymentReceipt])] = 
  batch.map(order => order -> paymentGateway.chargeSafe(order))

// Розсилка: неможливо розсинхронізувати адресата та результат
processed.foreach {
  case (order, Right(receipt)) => emailService.sendReceipt(order.email, receipt)
  case (order, Left(error))    => log.warn(s"Order ${order.id} failed: $error")
}
```

> **Як читати `Right` та `Left` (мнемонічне правило):**  
> У функціональних мовах тип `Either[Left, Right]` представляє два взаємовиключні результати:
> - **`Right`** (від англ. *right* — «правильний», «успішний») — зберігає **успішне значення** (`receipt`). Якщо все добре — ми «праві».
> - **`Left`** — зберігає **помилку або причину збою** (`error`).  
> Помилка стає не небезпечним винятком у runtime, а звичайним типізованим значенням, яке компілятор зобов'язує явно розібрати через pattern matching (`case Right` / `case Left`).

**Інженерний висновок:**  
В імперативному коді обробка помилок через `try-catch` та мутабельні списки випадає із загального потоку даних і створює приховані зсуви індексів.  
У функціональному стилі ми підключаємо **функцію як громадянина першого класу**: передаємо чисту функцію-трансформатор у метод `map`. При цьому сама помилка стає не винятком, а **типізованим значенням** (`Either`), надійно зафіксованим поруч із даними.

> **Що означає «First-Class Citizen» (громадянин першого класу):**  
> В Computer Science це будь-яка сутність, яку можна:
> 1. Присвоїти змінній.
> 2. Передати аргументом у функцію.
> 3. Повернути з функції як результат.
> 4. Зберегти в колекцію.
> 
> У наведеному коді є два прояви цієї концепції:
> - **Функція як громадянин першого класу:** функція обробки `order => ...` передається як аргумент у метод вищого порядку `batch.map(...)`.
> - **Помилка як значення першого класу (First-Class Value):** `Either` робить помилку звичайним об'єктом даних (значенням), яке спокійно лежить у списку, замість того, щоб руйнувати потік виконання викликом `throw new Exception()`.

## 2. Функція як значення (First-Class Citizens)

У класичних ООП-мовах методи не можуть існувати самі по собі — вони завжди жорстко «прив'язані» до класу чи об'єкта. У Scala ж **функція — це повноправне значення** (як число `42` чи рядок `"hello"`).

Але тут виникає інженерний парадокс: **Scala працює на JVM**.  
У байткоді віртуальної машини Java взагалі не існує типу даних «функція». Процесор JVM оперує лише класами, інтерфейсами та методами. Як же Scala примудряється зберігати функції у змінних та колекціях?

---

### 2.1. Місток від ООП: Чому Scala створила Трейт (`trait`), а не взяла Java-інтерфейс?

У Java контракти поведінки описують через `interface`. У Scala аналогічний базовий будівельний блок називається **трейтом (`trait`)**.

Чому творець Scala Мартін Одерськи не обмежився стандартними Java-інтерфейсами?
1. **Обмеженість старої Java:** На момент створення Scala інтерфейси в Java могли містити *виключно* абстрактні методи без тіла (default methods у Java з'явилися лише через 10 років у Java 8).
2. **Потужна композиція (Mixins):** Трейт у Scala задумувався як гнучкий модуль. Він може містити як абстрактні методи, так і **готову реалізацію коду, поля та стан**. Один клас може «підмішати» (mixin) кілька трейтів без проблем множинного спадкування.

Приклади оголошення трейтів у Scala 3:

```scala
// 1. Чистий контракт (як класичний інтерфейс Java):
trait Validator:
  def isValid(value: String): Boolean

// 2. Трейт із готовою реалізацією коду:
trait Logger:
  def log(msg: String): Unit = println(s"[LOG] $msg")

// 3. А ось так у стандартній бібліотеці Scala описано саму функцію:
//    -A: вхідний аргумент (контраваріантний, аналог <? super A> в Java)
//    +B: результат виклику (коваріантний, аналог <? extends B> в Java)
trait Function1[-A, +B]:
  def apply(x: A): B
```

Компілятор Scala транслює трейти у звичайні `.class`-файли інтерфейсів JVM.

> **💡 Generics у Scala проти Java: що означають `[-A, +B]`?**  
> 1. **Синтаксис:** Якщо в Java узагальнені типи (generics) пишуться в кутових дужках `Function<A, B>`, то в Scala — у квадратних `Function1[A, B]`.  
> 2. **Вайлдкарди та правило PECS:**  
>    * **У Java (Use-site variance):** щоб зробити метод гнучким, розробник щоразу пише громіздкі вайлдкарди за правилом PECS (*Producer Extends, Consumer Super*):  
>      `void handle(Function<? super A, ? extends B> f)`
>    * **У Scala (Declaration-site variance):** варіативність фіксується **один раз в оголошенні самого трейту**:
>      * **`-A` (Consumer / Вхід):** контраваріантність (аналог `? super A`). Функція споживає `A`, тому безпечно може прийняти ширший (базовий) тип аргументу.
>      * **`+B` (Producer / Вихід):** коваріантність (аналог `? extends B`). Функція продукує результат, тому гарантує повернення точнішого підтипу.  
> 
> Завдяки цьому в коді Scala не потрібно щоразу вручну писати wildcards — безпечне підставляння типів працює автоматично.

### 2.2. Як функція стає об'єктом у пам'яті (Function1 та apply)

Тепер парадокс розв'язано:  
Щоб функція існувала на JVM як об'єкт, стандартна бібліотека Scala надає сімейство готових трейтів: **`Function1[A, B]`** (функція з 1 параметром), **`Function2`** (з 2 параметрами) і так далі аж до `Function22`.

Коли ми записуємо поведінку у звичайну незмінну змінну `val`, компілятор створює екземпляр трейту `Function1`:

```scala
//            [Тип функції]      [Параметр]    [Вираз / Тіло]
val isAdult: (Int) => Boolean =    (age)    => (age >= 18)

// Виклик:
isAdult(20) // true
```

#### Чому працює виклик `isAdult(20)`? (Магія методу `apply`)
У Scala круглі дужки біля будь-якого об'єкта `obj(x)` компілятор автоматично перетворює на виклик методу **`obj.apply(x)`**.  
Рядок `isAdult(20)` насправді компілюється в **`isAdult.apply(20)`**. Жодної містики: функція — це просто об'єкт трейту з методом `apply`!

#### 🧠 Міні-тест: який трейт `FunctionN` працює під капотом?

Спробуйте визначити трейт для чотирьох різних випадків:

**1. Функція з двома параметрами:**
```scala
val multiply: (Int, Int) => Int = (a, b) => a * b
```
<details markdown="1">
<summary>Відповідь</summary>

* **Трейт:** `Function2[Int, Int, Int]`.  
  *Перші два `Int` — це типи вхідних параметрів `(a, b)`, а третій `Int` — це тип результату.*
* **Виклик під капотом:** `multiply(3, 4)` компілюється в `multiply.apply(3, 4)`.
</details>

**2. Функція без вхідних параметрів (генератор):**
```scala
val randomToken: () => String = () => java.util.UUID.randomUUID().toString
```
<details markdown="1">
<summary>Відповідь</summary>

* **Трейт:** `Function0[String]`.  
  *Вхідних параметрів 0, тому єдиний тип у квадратних дужках — це тип результату (`String`).*
* **Виклик під капотом:** `randomToken()` компілюється в `randomToken.apply()`.
</details>

**3. Функція з трьома параметрами (розрахунок доставки):**
```scala
val deliveryCost: (Double, Double, Boolean) => Double = 
  (weight, distance, isExpress) => (weight * 10) + (distance * 2) * (if isExpress then 1.5 else 1.0)
```
<details markdown="1">
<summary>Відповідь</summary>

* **Трейт:** `Function3[Double, Double, Boolean, Double]`.  
  *Перші три типи `Double, Double, Boolean` — це вхідні параметри, а останній четвертий `Double` — тип результату.*
* **Виклик під капотом:** `deliveryCost(5.0, 50.0, true)` компілюється в `deliveryCost.apply(5.0, 50.0, true)`.
</details>

**4. Метод `def` усередині об'єкта, присвоєний у змінну:**
```scala
object TaxService:
  def calculateVat(netAmount: Double): Double = netAmount * 0.20

val vatFn: (Double) => Double = TaxService.calculateVat
```
<details markdown="1">
<summary>Відповідь</summary>

* **Трейт:** `Function1[Double, Double]`.  
  *Один вхідний параметр `Double` + один тип результату `Double`.*
* **Що сталося під капотом:** Метод `def` сам по собі не є об'єктом, але компілятор через **Eta Expansion** автоматично загорнув його в об'єкт трейту `Function1[Double, Double]`.
* **Виклик під капотом:** `vatFn(100.0)` компілюється в `vatFn.apply(100.0)`, який делегує виконання методу `TaxService.calculateVat(100.0)`.
</details>

### 2.3. Функція в колекції

Оскільки функція є звичайним значенням, ми можемо зберігати набір різних алгоритмів у колекції та викликати їх динамічно:

```scala
// 1. Оголошуємо звичайні методи через def:
object DiscountRules:
  def blackFriday(price: Double): Double = price * 0.80
  def loyaltyCard(price: Double): Double = price * 0.95
  def clearance(price: Double): Double   = price * 0.50

// 2. Зберігаємо функції у звичайному списку:
val rules: List[(Double) => Double] = List(
  DiscountRules.blackFriday,
  DiscountRules.loyaltyCard,
  DiscountRules.clearance
)

// 3. Застосовуємо кожне правило до ціни 100.0:
val finalPrices: List[Double] = rules.map(_(100.0))
// Результат: List(80.0, 95.0, 50.0)
```

#### 💡 Демістифікація: Метод (`def`) проти Функції (`val`) та магія Eta Expansion

У студентів із бекграундом у Java чи C++ виникає закономірне запитання:  
*«Метод `blackFriday` оголошений через `def` усередині об'єкта. Метод у JVM — це не об'єкт, а просто байткод. Як він раптом опинився у списку `List[(Double) => Double]`?»*

Ось що відбувається під капотом:

* **Метод (`def`):** Це інструкція на рівні байткоду JVM, що належить класу. Метод сам по собі **не є об'єктом чи значенням** — його не можна покласти в змінну чи колекцію.
* **Функція-значення (`Function1`):** Це повноцінний об'єкт у пам'яті (Heap). Запис `(Double) => Double` — це компактний синтаксичний цукор для вже знайомого нам трейту-інтерфейсу **`Function1[Double, Double]`** (об'єкта функції **з одним вхідним параметром**, що містить метод `apply`).
* **Eta Expansion (Eta-розширення):** Коли компілятор бачить, що список очікує об'єкт типу `(Double) => Double` (тобто `Function1[Double, Double]`), а ви передаєте метод `def blackFriday`, він **автоматично генерує анонімний функціональний об'єкт-обгортку**:

```scala
// Компілятор за лаштунками перетворює метод на об'єкт Function1:
val blackFridayFunction: Function1[Double, Double] = new Function1[Double, Double] {
  override def apply(price: Double): Double = DiscountRules.blackFriday(price)
}
```

Жодної містики: завдяки **Eta Expansion** компілятор Scala на льоту перетворює будь-який службовий метод `def` на повноцінний об'єкт-значення першого класу.

## 3. Священна трійця: `map`, `filter`, `flatMap`

У реальному комерційному коді **понад 90% логіки на Scala** будується саме навколо цієї трійки операцій. Імперативні цикли `for`/`while` та мутабельні акумулятори у функціональному бекенді майже ніколи не пишуться: будь-яка обробка замовлень, аналітика чи робота з потоками Kafka зводиться до декларативного конвеєра.

> **Архітектурна аналогія: Конвеєр як мікро-ETL (Extract — Transform — Load)**  
> Кожен функціональний ланцюжок — це звичний для Big Data процес ETL прямо в оперативній пам'яті:
> * **Extract (Видобування):** Отримуємо початковий потік подій, батч замовлень чи вибірку з БД.
> * **Transform (Трансформація):**
>   * **`filter` (Очищення / Cleansing):** відкидаємо невалідні дані, заблоковані акаунти чи скасовані записи.
>   * **`map` (Проєкція та збагачення / Enrichment):** перетворюємо кожен елемент 1-в-1 (наприклад, перераховуємо ціну з урахуванням податків).
>   * **`flatMap` (Розплющення / Flattening):** розгортає вкладені структури. Наприклад, об'єднує списки куплених товарів усіх клієнтів в один спільний перелік або зв'язує кроки пошуку без ризику отримати `NullPointerException`.
> * **Load (Завантаження):** Отримуємо чистий готовий результат для збереження в БД або відправки споживачам.

```text
[ Extract: Сирі дані ] ──► filter (відсікання) ──► map / flatMap (трансформація) ──► [ Load: Результат ]
```

### 1. `map` — Проєкція 1-в-1
Трансформує кожен елемент колекції за заданою функцією. **Розмір колекції не змінюється**, змінюється тип або значення елементів.

```scala
case class Sensor(id: String, tempCelsius: Double)

val sensors = List(
  Sensor("A1", 20.0), 
  Sensor("B2", 35.5),
  Sensor("F451", 232.78) // ~451 °F — температура самозаймання паперу з роману Рея Бредбері
)

// Отримуємо тільки температури у Фаренгейтах:
val fahrenheit: List[Double] = sensors.map(s => (s.tempCelsius * 1.8 + 32).round.toDouble)
// List(68.0, 96.0, 451.0)
```

### 2. `filter` — Селекція (Відсікання шуму)
Залишає тільки ті елементи, для яких предикат повертає `true`.

```scala
// Знайти всі датчики з перегрівом:
val overheating: List[Sensor] = sensors.filter(_.tempCelsius > 30.0)
```

### 3. `flatMap` — Трансформація з розплющенням (`map` + `flatten`)

Назва методу буквально описує його роботу: **`flatMap = map + flatten`**.  
Він спочатку перетворює кожен елемент за допомогою функції (`map`), а потім «розплющує» отриману вкладену структуру на один рівень глибини (`flatten`).

Розгляньмо два головні сценарії з реального життя, де звичайний `map` не справляється.

---

#### Сценарій А: Зв'язок 1-до-багатьох (список списків)

Уявіть IT-команду. Кожен розробник володіє списком навичок (`List[String]`). Наше завдання — отримати єдиний загальний перелік навичок усієї команди:

```scala
case class Developer(name: String, skills: List[String])

val team = List(
  Developer("Оксана", List("Scala", "Akka")),
  Developer("Тарас",  List("Docker", "Kubernetes"))
)

// ❌ Звичайний map створює громіздкий "список списків" (List[List[String]]):
val nested: List[List[String]] = team.map(_.skills)
// Результат: List(List("Scala", "Akka"), List("Docker", "Kubernetes"))

// ✅ flatMap спочатку дістає списки, а потім зливає їх в один плоский перелік:
val allSkills: List[String] = team.flatMap(_.skills)
// Результат: List("Scala", "Akka", "Docker", "Kubernetes")
```

---

#### Сценарій Б: Ланцюжок пошуку без `NullPointerException` (контейнер `Option`)

Що таке **`Option`** у Scala? Це безпечна «коробка», в якій значення або є (`Some(значення)`), або відсутнє (`None`). Це функціональна заміна небезпечного `null`.

Уявіть типову бізнес-задачу з двох послідовних кроків:
1. Знайти користувача за ID у базі (користувача може не бути $\to$ `Option[User]`).
2. Отримати його робочий email (пошта в профілі не обов'язкова $\to$ `Option[String]`).

```scala
def findUser(id: Int): Option[User] = ...
def getEmail(user: User): Option[String] = ...

// ❌ Звичайний map запакує один Option в інший — вийде "коробка в коробці":
val nestedEmail: Option[Option[String]] = findUser(42).map(user => getEmail(user))

// ✅ flatMap автоматично усуває зайвий рівень обгортки (розплющує подвійний контейнер):
val cleanEmail: Option[String] = findUser(42).flatMap(user => getEmail(user))
```

**Чому це красиво та інженерно ефективно:**  
* **Код без сміття (Zero Boilerplate):** Якщо користувача не знайдено — результатом одразу буде `None`. Якщо користувач є, але пошти немає — теж `None`. І лише коли обидва кроки успішні — ми отримаємо `Some("user@work.com")`.  
* **Апаратна перевага для CPU (Branch Prediction):** Ці функціональні ланцюги повністю **прибирають спагеті з `if`-розгалужень** (`if (user != null) { if (email != null) ... }`), які буквально не дозволяють сучасним процесорам працювати швидко. Сучасні CPU використовують глибокий конвеєр інструкцій (Pipeline) та апаратне передбачення переходів (Branch Predictor). Коли через непередбачувані бізнес-дані розгалуження хибить (**Branch Misprediction**), процесор змушений повністю скидати конвеєр (Pipeline Flush) і починати зчитування заново (штраф до **15–20 тактів CPU** на кожен промах). Ланцюжок `flatMap`/`map` перетворює логіку на лінійний потік інструкцій, забезпечуючи процесору максимальну швидкість виконання.

#### 📦 Практичний довідник: Як дістати значення з `Option` (`Some` vs `None`)

Отримавши `cleanEmail: Option[String]`, виникає закономірне запитання: *«Як тепер безпечно витягти чистий рядок із коробки `Some`?»*

Ось 3 перевірені способи (та 1 фатальний антипатерн):

1. **`getOrElse(default)` — резервне значення / запасний варіант (Fallback):**
   Найпопулярніший спосіб. Якщо всередині є значення (`Some`) — дістає його, а якщо порожньо (`None`) — повертає вказане резервне значення за замовчуванням:
   ```scala
   val email: String = cleanEmail.getOrElse("no-reply@company.com")
   ```

2. **Pattern Matching (`match / case`) — коли для `None` потрібна окрема логіка обчислення:**
   У чистому ФП `match` — це вираз (expression), який повертає значення без побічних ефектів (наприклад, формує список адресатів):
   ```scala
   val recipients: List[String] = cleanEmail match
     case Some(email) => List(email)
     case None        => List("backup-admin@company.com") // список із запасним контактом
   ```

3. **Функціональний шлях (опрацювання без ручного розпакування):**
   У функціональному стилі значення часто взагалі не дістають із коробки, а продовжують конвеєр:
   * **Чиста трансформація (`.map`)** — змінити значення всередині контейнера, залишаючись в `Option`:
     ```scala
     // Якщо Some("alex@corp.com") -> Some("corp.com"), якщо None -> None:
     val domain: Option[String] = cleanEmail.map(_.split("@")(1))
     ```
   * **Побічний ефект на межі системи (`.foreach`)** — метод повертає `Unit` (нічого) і виконує дію **тільки якщо** значення присутнє (`Some` = 1 раз, `None` = 0 разів без жодних `if`):
     ```scala
     // Безпечна заміна імперативного if (email != null):
     cleanEmail.foreach(email => emailService.sendReceipt(email, receipt))
     ```

> ⚠️ **Антипатерн: метод `.get`**  
> Ніколи не викликайте `cleanEmail.get` у продакшені! Якщо всередині виявиться `None`, ви отримаєте `NoSuchElementException: None.get`. Це той самий `NullPointerException`, але в іншій обгортці.

> 💡 **Куди рухатися далі з `Option`?**  
> Повний розбір контейнера `Option` — чому `Some` та `None` утворюють закриту алгебраїчну ієрархію (`sealed trait`), як елегантно обгортати спадковий Java-код (`Option(javaValue)`) та будувати залізничні конвеєри через `for-comprehension` — ми детально розберемо у наступній [Лекції 03: Залізничне програмування (Railway-Oriented)](03_railway_oriented_programming.md).

### 4. За межами трійці: Групування (`groupBy`) та сортування (`sortBy`)

У промислових сервісах обробка даних рідко завершується простими `map` та `filter`. Дуже часто перед нами стоїть завдання, аналогічне SQL-запиту з агрегацією:  
`SELECT donor, SUM(amount) FROM donations GROUP BY donor ORDER BY sum DESC LIMIT n`.

У класичному ООП/Java без Streams це вимагало б ручного циклу з `Map<String, Double>` та постійних перевірок `map.containsKey` чи `map.put(..., map.get(...) + amount)`.  
У чистому функціональному підході ми збираємо **декларативний конвеєр трансформації форми даних** (саме так реалізовано аналітику у [Практиці 03: Банка донатів](p03_javish_donation_jar.md)):

```scala
case class Donation(donor: String, amount: Double)

val donations = List(
  Donation("Олена", 500.0),
  Donation("Андрій", 1200.0),
  Donation("Олена", 700.0),
  Donation("Марія", 300.0)
)

val topDonors: List[(String, Double)] = donations
  .groupBy(_.donor)                                               // 1. GROUP BY donor: Map("Олена" -> List(Donation(500), Donation(700)), ...)
  .map { case (donor, list) => (donor, list.map(_.amount).sum) }  // 2. Звичайний map: рахуємо суму донатів для кожного донора
  .toList                                                         // 3. Перетворюємо мапу в список пар: List(("Олена", 1200.0), ...)
  .sortBy { case (donor, sum) => -sum }                           // 4. ORDER BY sum DESC: сортуємо за мінус-сумою (-1200 < -300, більші йдуть першими)
  .take(2)                                                        // 5. LIMIT 2: вибірка топ-2 донаторів
```

#### Анатомія трансформації форми даних (Data Flow Trace):

| Крок | Метод | Аналог у SQL | Тип результату | Стан даних на кроці |
| :---: | :--- | :--- | :--- | :--- |
| **0** | *Вхід* | `FROM donations` | `List[Donation]` | 4 сирих факти донатів |
| **1** | `.groupBy(_.donor)` | `GROUP BY donor` | `Map[String, List[Donation]]` | `"Олена" -> [Donation(500), Donation(700)]`, `"Андрій" -> [Donation(1200)]`... |
| **2** | `.map { case ... }` | `SELECT donor, SUM(amount)` | `Map[String, Double]` | Значення згорнуті в суми: `"Олена" -> 1200.0`, `"Андрій" -> 1200.0` |
| **3** | `.toList` | *(матеріалізація списку)* | `List[(String, Double)]` | Список пар-кортежів: `("Олена", 1200.0)`, `("Андрій", 1200.0)`... |
| **4** | `.sortBy { case ... => -sum }` | `ORDER BY sum DESC` | `List[(String, Double)]` | Відсортовано за спаданням (мінус перед `sum` розвертає порядок) |
| **5** | `.take(2)` | `LIMIT 2` | `List[(String, Double)]` | Топ-2 донатори: `List(("Олена", 1200.0), ("Андрій", 1200.0))` |

> 💡 **Сила функціонального конвеєра**  
> Замість 15 рядків спагеті-коду на Java з мутабельними `HashMap`, перевірками `containsKey` та ручним сортуванням колекції — ми отримали декларативний ланцюжок, який читається зверху вниз як послідовний бізнес-пайплайн. Жодної мутабельної змінної!

> ❓ **Чому на кроці 2 використовується звичайний `map`, а не `flatMap`?**  
> * **Зв'язок 1-в-1 $\to$ тільки `map`:** Для кожного вхідного донора ми отримуємо **рівно одну** підсумкову пару: `("Олена", List(500, 700)) ──► ("Олена", 1200.0)`. Було 3 унікальні донори — залишилося 3 підсумкові записи.
> * **Коли знадобився б `flatMap`?** Лише якщо трансформація одного елемента породжує **колекцію** (0, 1 або багато нових значень). Якби ми використали `flatMap` тут, нам довелося б безглуздо загортати результат у `List((donor, sum))` лише заради того, аби `flatMap` його тут же розплющив.

## 4. Анатомія короля функціонального програмування: `foldLeft`

Що робити, якщо треба порахувати суму чисел, згрупувати об'єкти чи знайти максимум?  
В імперативному стилі заводиться мутабельна змінна `var acc = 0`, яка перезаписується на кожному кроці.  
У ФП для цього існує універсальна операція — **згортка (`foldLeft`)**.

### Метафора «Снігової кулі»
Уявіть снігову кулю, яку котять засніженим схилом:
1. **Початковий стан (Zero / Initial value):** Маленька сніжка в руках (наприклад, `0` або порожній список).
2. **Список елементів:** Сніжинки на траві.
3. **Функція кроку (Step):** Як саме нова сніжинка налипає на кулю `(Куля, Сніжинка) => НоваКуля`.

```scala
val numbers = List(1, 2, 3, 4)

// foldLeft(початкове_значення) { (акумулятор, елемент) => новий_акумулятор }
val sum = numbers.foldLeft(0) { (acc, x) => acc + x }
```

### Трасування роботи `foldLeft(0)(_ + _)`:
| Крок | Вхідний елемент | Акумулятор ДО кроку | Формула | Акумулятор ПІСЛЯ кроку |
| :---: | :---: | :---: | :---: | :---: |
| **Старт** | — | — | — | **`0`** (базове значення) |
| **1** | `1` | `0` | `0 + 1` | `1` |
| **2** | `2` | `1` | `1 + 2` | `3` |
| **3** | `3` | `3` | `3 + 3` | `6` |
| **4** | `4` | `6` | `6 + 4` | **`10`** (фінал) |

---

### 🛡️ Інженерне зіставлення: Чому неконтрольована агрегація в ООП вибухає пам'яттю, а у ФП — ні

Уявіть типову сервісну задачу: на бекенд надходить батч бізнес-замовлень (`orders`). Нам потрібно виконати дві звичні дії: **порахувати загальну суму батчу** та **залогувати компактний рядок аудиту**.

#### 1. Як це роблять у Java/ООП і на які граблі наступають

* **Пастка №1 (При підрахунку суми) — Небезпечний мутабельний стан:**
  ```java
  // Працює швидко і стек O(1), але є MUTABLE STATE:
  double total = 0.0;
  for (Order order : orders) {
      total += order.getAmount(); // пряма мутація пам'яті на кожній ітерації
  }
  ```
  В асинхронних чи реактивних пайплайнах (Netty, Reactor, Virtual Threads) спільна мутабельна змінна — це гарантований стан гонитви (Race Condition) або потреба у важких блокуваннях (`synchronized`).

* **Пастка №2 (При спробі залогувати батч) — Вибух на 6 GB Heap через `super.toString()`:**  
  У складних ООП-ієрархіях класи наслідують поля та поведінку: `AuditEntity -> BaseOrder -> EnterpriseOrder`.  
  Розробник пише в коді «невинний» рядок для діагностики:
  ```java
  log.info("Processing batch: {}", orders); // Неявно смикає .toString() для кожного об'єкта
  ```
  **Що пішло не так на проді:**
  1. Кожен клас при перевизначенні писав `return "EnterpriseOrder{" + super.toString() + ...}`.
  2. Виклик `super.toString()` тягнув за собою поля предка, той — історію клієнта, а та — зворотні посилання на пов'язані сутності!
  3. Виникла неконтрольована каскадна рекурсія по всьому графу зв'язаних об'єктів.
  4. Під капотом `StringBuilder` гарячково подвоював масиви символів у купі: $16 \to 32 \to \dots \to 500\text{ MB} \to 2\text{ GB} \to 6\text{ GB}$!
  5. Повний параліч збирача сміття (Stop-The-World) і фатальний краш усього контейнера: **`java.lang.OutOfMemoryError: Java heap space`**.

---

#### 2. Як це розв'язує Scala: Контрольована лінійна згортка `foldLeft`

У функціональному підході моделі даних — це пласкі, незмінні `case class` без спадкування поведінки та прихованих викликів `super`:

```scala
case class Order(id: String, amount: Double)
val orders = List(Order("ord-1", 100.0), Order("ord-2", 250.0), Order("ord-3", 50.0))
```

> 💡 **Примітка про `case class`:**  
> Це незмінний контейнер для чистих даних (можете уявляти його як потужніший аналог Java-`record`). Усі подробиці про `case class`, деструктуризацію та алгебраїчні типи даних (ADT) ми детально розберемо у наступній [Лекції 03: Залізничне програмування](03_railway_oriented_programming.md).

Обидві задачі розв'язуються через **явний функціональний `foldLeft`**:

```scala
// 1. Агрегація суми (без жодної змінної var чи блокувань):
val total: Double = orders.foldLeft(0.0)((acc, order) => acc + order.amount)

// 2. Безпечний компактний аудит-рядок (повний контроль над виділенням пам'яті на кожному кроці):
val auditLog: String = orders.foldLeft(new java.lang.StringBuilder("Batch: ")) { (sb, order) =>
  sb.append(s"[${order.id}:${order.amount}]")
}.toString
```

* **Жодного прихованого розгортання графа:** Інженер чітко декларує, які саме поля беруть участь у згортці. Жодних `super.toString()`, циклічних залежностей чи зайвих даних.
* **Безпека стеку та пам'яті ($O(1)$ Stack-Safe):** Проміжний акумулятор оновлюється одразу на льоту ($0.0 \to 100.0 \to 350.0 \to 400.0$). Компілятор Scala перетворює `foldLeft` у високоефективний байткод-цикл.
* **Повна імутабельність та ізоляція:** Оскільки немає спільного змінного стану (`total += ...`), різні потоки можуть безпечно читати одні й ті самі колекції без ризику виникнення станів гонитви (Race Conditions).
*(Чому в пункті 2 використано `StringBuilder`? Це інженерна оптимізація: пряма конкатенація `String` у циклі створювала б $N$ непотрібних об'єктів у Heap. А в чисто декларативному стилі ту саму дію записують ще простіше: `orders.map(o => s"[${o.id}:${o.amount}]").mkString("Batch: ", "", "")`).*

> ⚠️ **Чи розпаралелюється сам `foldLeft` між ядрами CPU?**  
> **Ні!** `foldLeft` за своєю природою — **строго послідовний** (sequential). Крок №3 не може розпочатися, доки крок №2 не обчислить проміжний акумулятор: `acc0 ──► acc1 ──► acc2`.  
> Його «безпека для потоків» полягає у **відсутності спільного мутабельного стану**, а не у внутрішньому паралелізмі. Якщо вам потрібна паралельна обробка на всіх ядрах процесора або в кластері (Fork-Join / Apache Spark) — використовують метод **`fold`** (без префікса `Left`), який вимагає асоціативності операції.

> 🧭 **Мнемонічне правило інженера (Що і коли обирати):**  
> * **Потрібно порахувати одне підсумкове значення** (сума, баланс, єдиний рядок або конфіг) із багатьох елементів $\to$ обирайте **`foldLeft`** ($N$ елементів $\to$ $1$ результат).  
> * **Потрібно згрупувати та порахувати по кошиках** (розбити за категоріями, клієнтами, статусами) $\to$ зв'язка **`groupBy` + `map`** (аналог SQL `GROUP BY` + агрегація).

<details markdown="1">
<summary>🔍 Чому метод називається саме foldLeft? Навіщо тоді взагалі існує foldRight?</summary>

* **Чому для звичайних колекцій беруть `foldLeft`:**  
  Він обчислює акумулятор одразу зліва направо, працює в константному розмірі стеку ($O(1)$) і захищений від `StackOverflowError`.

* **Для чого комп'ютерні вчені створили `foldRight`:**  
  1. **Зберігає природний порядок елементів:** при побудові нового списку через швидке додавання на початок (`x :: acc`), `foldLeft` перевертає список у зворотному порядку (`List(3, 2, 1)`), що вимагає виклику `.reverse()`. А `foldRight` додає елементи з кінця і відтворює початковий порядок `List(1, 2, 3)` за один прохід.  
  2. **Вміє працювати з нескінченними потоками (`LazyList`):** оскільки `foldRight` обчислює значення ліниво, він може достроково перервати згортку (short-circuiting), наприклад, знайти перший збіг і зупинитися. `foldLeft` на нескінченному потоці завис би навічно, бо він завжди намагається дійти до кінця списку.
</details>

#### 3. Підсумкова матриця зіставлення: Java `for` проти Scala `foldLeft`

| Критерій | ООП / Java (цикл `for` з мутацією) | Scala (`foldLeft`) |
| :--- | :--- | :--- |
| **Мутабельний стан** | ❌ Є (`double total += ...`) | ✅ **Немає** (чистий незмінний код) |
| **Пам'ять стеку (Call Stack)** | ✅ $O(1)$ (константний розмір) | ✅ **$O(1)$ (Stack-Safe)** |
| **Багатопотокова безпека** | ❌ Стан гонитви (потребує блокувань) | ✅ **Безпечно (відсутній спільний стан)** |
| **Стиль коду** | Імперативний бойлерплейт | ✅ **Декларативний конвеєр** |
| **Внутрішній паралелізм** | ❌ Строго послідовний | ❌ **Строго послідовний** (для паралелізму — `fold`) |

---

### 💡 Інженерний інсайт: Усі трансформації — це насправді `foldLeft`!
Будь-яка стандартна операція над колекціями — це лише частковий випадок `foldLeft`:

```scala
// Як насправді реалізовано map через foldLeft (O(N) завдяки швидкому :: та .reverse):
def myMap[A, B](list: List[A])(f: A => B): List[B] =
  list.foldLeft(List.empty[B])((acc, elem) => f(elem) :: acc).reverse

// Як реалізовано filter через foldLeft:
def myFilter[A](list: List[A])(predicate: A => Boolean): List[A] =
  list.foldLeft(List.empty[A]) { (acc, elem) => 
    if predicate(elem) then elem :: acc else acc 
  }.reverse
```

> ❓ **«Зачекайте, а звідки в реалізації `myFilter` взявся `if`? Ми ж вчимося писати без нього!»**  
> Саме в цьому полягає головна інженерна магія! Метод **`filter` існує якраз для того, щоб назавжди ізолювати та поховати оператор `if` всередині себе**.  
> Ви один раз інкапсулюєте бінарний вибір у бібліотечному `filter`, і після цього 100 000 рядків вашого бізнес-коду стають ідеально лінійними декларативними конвеєрами без жодного умовного переходу!
> 
> *(До речі, у чистому ФП навіть цей внутрішній вибір можна записати без ключового слова `if`: через `acc ++ Option.when(predicate(elem))(elem)`).*

## 5. Стан як згортка подій (Місток до Event Sourcing)

У розподілених системах стан сервера ніколи не зберігають у мутабельних змінних.  
Замість цього стан системи моделюється як **чиста згортка незмінного журналу подій (Event Log)**:

```
[Подія 1: Створено рахунок] ──┐
[Подія 2: Поповнення +500 ]  ─┼──► foldLeft(Початковий_стан) ──► Баланс: 400 грн
[Подія 3: Списання  -100  ] ──┘
```

Саме за цим принципом працює ігровий рушій нашого наскрізного проєкту [23_runner (Практика 06)](p06_engine_architecture.md):
```scala
// Ігровий світ на 100-му тіку — це результат згортки 100 дій ботів:
val finalState = actionsHistory.foldLeft(initialState) { (state, action) =>
  Engine.nextTick(state, action)
}
```

## 6. Композиція функцій: Трубопровід без проміжних змінних

**Інша типова ситуація:** послідовна обробка даних (очистити рядок $\to$ вирахувати податок $\to$ сформувати чек). 

Без композиції розробник змушений обирати між двома незручними варіантами:

```scala
// ❌ Варіант 1: Тимчасові змінні (потрібні рівно на один рядок, засмічують метод)
val rawInput    = "  10000  "
val parsedValue = parseRawInput(rawInput)
val calculated  = calculateTax(parsedValue)
val finalResult = formatReceipt(calculated)

// ❌ Варіант 2: Вкладена «матрьошка» (читається неприродно — зсередини назовні, справа наліво)
val finalResult = formatReceipt(calculateTax(parseRawInput("  10000  ")))
```

У функціональному підході функції — це **ланки неперервного конвеєра**. Вони з'єднуються напряму через композицію `andThen` (природний порядок: зліва направо, «спочатку A, потім B»):

```scala
val parseRawInput: String => Int    = str => str.trim.toInt
val calculateTax: Int => Double     = income => income * 0.18
val formatReceipt: Double => String = tax => f"Податок: $tax%.2f грн"

// ✅ Будуємо готовий конвеєр: (A => B) andThen (B => C) andThen (C => D)
val pipeline: String => String = parseRawInput andThen calculateTax andThen formatReceipt

// Пропускаємо сирі дані крізь зафіксований інструмент:
pipeline("  10000  ") // "Податок: 1800.00 грн"
```

Жодних зайвих імен, жодного проміжного стану. Кожна функція залишається ізольованою, легкою для тестування та повторного використання.

## Підсумок лекції

* **Немає індексів — немає багів:** цикли `for/while` замінюються на декларативні пайплайни `filter`, `map`, `fold`.
* **Функція — це звичайне значення:** її можна передавати в аргументи, групувати в колекції та компонувати.
* **`foldLeft` — це ядро обчислень:** будь-який накопичувальний процес (підрахунок грошей, стан гри, аналіз логів) є чистою згорткою без мутацій.

## Контрольні питання для самоперевірки

<details markdown="1">
<summary>1. Чому foldLeft називається саме "Left" і чим він відрізняється від foldRight?</summary>

`foldLeft` починає рух від першого (лівого) елемента списку до останнього. Він є **хвостово-рекурсивним (Tail-Recursive)** і виконується в константному стеку ($O(1)$ пам'яті), тому ніколи не викличе `StackOverflowError`. Натомість `foldRight` розгортається справа наліво і накопичує фрейми у стеку викликів, тому на мільйонних списках він може звалити JVM.
</details>

<details markdown="1">
<summary>2. Як за допомогою filter та map реалізувати підрахунок суми зарплат співробітників відділу QA?</summary>

```scala
val qaBudget = employees
  .filter(_.department == "QA")
  .map(_.salary)
  .sum // або .foldLeft(0.0)(_ + _)
```
Тут жодна проміжна колекція не мутує, код читається як звичайне англійське речення.
</details>

<details markdown="1">
<summary>3. Чому функція, яку передають у reduce/fold при паралельних обчисленнях, має бути асоціативною?</summary>

Асоціативність означає, що $(a + b) + c = a + (b + c)$. Якщо операція асоціативна (як додавання чи множення), список можна розрізати на 16 шматків, обчислити згортку окремо на 16 ядрах процесора у будь-якому порядку і склеїти результати. Якщо операція неасоціативна (як віднімання чи ділення), паралельне обчислення видасть випадковий неправильний результат.
</details>

<details markdown="1">
<summary>4. Що відбувається під капотом у виразі donations.groupBy(_.donor).map { case (donor, list) => ... }?</summary>

1. `groupBy(_.donor)` розбиває вихідний список на мапу списків `Map[String, List[Donation]]`, де ключ — ім'я донора, а значення — список усіх його донатів.
2. `.map { case (donor, list) => (donor, list.map(_.amount).sum) }` обробляє кожну пару: бере список донатів конкретного донора і рахує його суму, формуючи чисту підсумкову `Map[String, Double]` без жодних проміжних `var` чи мутабельних `HashMap`.
</details>
