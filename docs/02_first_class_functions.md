## Питання для розминки

<details markdown="1">
<summary>1. Чому цикл for — найнебезпечніше місце для прихованих багів в інженерному коді?</summary>

Цикл `for (int i = 0; i < n; i++)` вимагає керування трьома речами одночасно: початковим індексом, кроком імплементації та умовою виходу. Помилка на одиницю (**Off-by-one bug**), випадкова зміна лічильника всередині тіла або вихід за межі пам'яті трапляються щодня. Функціональний конвеєр оперує колекцією як цілісним значенням — там **фізично немає індексів**, тому такий клас багів виключений на рівні дизайну.
</details>

<details markdown="1">
<summary>2. Що спільного між промисловим конвеєром заводу та функціональним кодом?</summary>

На сучасному автозаводі робітники та роботи-зварювальники стоять нерухомо на своїх місцях. Конвеєрна стрічка рухає **незмінні деталі крізь нерухомі інструменти**. У ФП функції — це зафіксовані інструменти, а дані протікають крізь них без побічних змін навколишнього середовища.
</details>

<details markdown="1">
<summary>3. Що означає термін «функція як громадянин першого класу» (First-Class Citizen)?</summary>

Це означає, що функція позбавлена статусу "другорядного службового коду". Вона стає **таким самим звичайним значенням**, як число `42` чи рядок `"Hello"`: її можна присвоїти змінній, покласти в масив, передати аргументом в інший метод або повернути як результат обчислень.
</details>

## 1. Архітектурний кейс: Катастрофа «Off-by-One» на Чорну п'ятницю

**Контекст:** Великий маркетплейс обробляє святковий пік платежів (15 000 замовлень на секунду).  
Бекенд написаний класичним імперативним стилем: батчі замовлень з черги вичитуються масивом та обробляються циклом `for`:

```java
// ❌ Типовий імперативний код у платіжному сервісі:
List<PaymentResult> results = new ArrayList<>();
for (int i = 0; i <= batch.size(); i++) { // УВАГА: знак <= замість <
    Order order = batch.get(i);
    if (order.isVerified()) {
        results.add(paymentGateway.charge(order));
    }
}
```

### Що пішло не так:
1. Джуніор-розробник під час термінового виправлення випадково змінив `<` на `<=`.
2. На останній ітерації `batch.get(batch.size())` викинув `IndexOutOfBoundsException`.
3. Виняток обірвав обробку батчу: половина замовлень була списана, а інша — зависла.
4. Транзакція впала посередині, сервіс почав ретраїти весь батч знову, що спричинило **подвійне списання грошей у клієнтів**. Збитки склали мільйони гривень.

```scala
// ✅ Функціональний еквівалент:
val results: List[PaymentResult] = batch
  .filter(_.isVerified)
  .map(paymentGateway.charge)
```

**Інженерний висновок:**  
У функціональному коді **неможливо** помилитися індексом або вийти за межі колекції. Колекція є самодостатнім потоком даних, а не масивом сирих байтів із ручним покажчиком.

## 2. Функція як значення (First-Class Citizens)

У мовах на кшталт C або старій Java функції існували тільки як "методи класів". Їх не можна було відірвати від об'єкта.  
У Scala функція — це повноправний об'єкт.

### 1. Функція у змінній
Ми можемо призначити поведінку звичайній незмінній `val`:

```scala
val isAdult: Int => Boolean = age => age >= 18

// Виклик:
isAdult(20) // true
```

### 2. Функція в колекції
Ми можемо створити список алгоритмів і застосовувати їх динамічно (саме так ми будували медичний консиліум у [Практиці 05](p05_heart_disease_triage.md)):

```scala
// Список незалежних функцій-діагностів:
val evaluators: List[PatientRecord => Diagnosis] = List(
  AhaProtocol.evaluate,
  FraminghamScore.evaluate,
  DukeScore.evaluate
)

// Одночасний запуск усіх діагностів для одного пацієнта:
val verdicts: List[Diagnosis] = evaluators.map(evaluator => evaluator(patient))
```

#### 💡 Демистифікація: Метод (`def`) проти Функції (`val`) та магія Eta Expansion
У студентів із бекграундом у Java чи C++ виникає справедливе запитання:  
*«Метод `AhaProtocol.evaluate` оголошений через `def` всередині `object`. Як він раптом опинився у списку значень `List[PatientRecord => Diagnosis]`?»*

* **Метод (`def`):** Це інструкція на рівні байткоду JVM, що належить класу. Метод сам по собі **не є об'єктом** — його не можна просто так покласти в кишеню чи змінну.
* **Функція-значення (`Function1`):** Це справжній об'єкт у купі (Heap), який має метод `apply`.
* **Eta Expansion:** Коли компілятор Scala 3 бачить, що контекст очікує значення типу `PatientRecord => Diagnosis`, а ви передаєте метод `AhaProtocol.evaluate`, він **автоматично генерує анонімну функцію-обгортку**:
  ```scala
  // Компілятор за лаштунками робить це за вас:
  val lambda: PatientRecord => Diagnosis = p => AhaProtocol.evaluate(p)
  ```
Жодної містики: метод на льоту "підноситься" до повноцінного функціонального об'єкта.

## 3. Священна трійця: `map`, `filter`, `flatMap`

Будь-яка обробка масивів у корпоративному софті зводиться до трьох фундаментальних дій:

```
[ Початкові дані ] ──► filter (відсікання) ──► map (трансформація) ──► Результат
```

### 1. `map` — Проєкція 1-в-1
Трансформує кожен елемент колекції за заданою функцією. **Розмір колекції не змінюється**, змінюється тип або значення елементів.

```scala
case class Sensor(id: String, tempCelsius: Double)

val sensors = List(Sensor("A1", 20.0), Sensor("B2", 35.5))

// Отримуємо тільки температури у Фаренгейтах:
val fahrenheit: List[Double] = sensors.map(s => s.tempCelsius * 1.8 + 32)
// List(68.0, 95.9)
```

### 2. `filter` — Селекція (Відсікання шуму)
Залишає тільки ті елементи, для яких предикат повертає `true`.

```scala
// Знайти всі датчики з перегрівом:
val overheating: List[Sensor] = sensors.filter(_.tempCelsius > 30.0)
```

### 3. `flatMap` — Універсальний клей контекстів (не лише для списків!)

Часто початківці вважають, що `flatMap` потрібен лише для того, щоб «розплющувати» вкладені списки. Це лише 10% його сили.  
**`flatMap` — це універсальний клей для послідовних обчислень усередині контекстів (`List`, `Option`, `Either`, `Future`).**

#### А. Розплющення колекцій (контекст множинності):
Коли трансформація породжує на кожен елемент новий список, `map` дасть вкладену «матрьошку» `List[List[T]]`:

```scala
case class Developer(name: String, skills: List[String])

val team = List(
  Developer("Оксана", List("Scala", "Akka")),
  Developer("Тарас", List("Docker", "Kubernetes"))
)

// ❌ map дає List[List[String]]:
val nested: List[List[String]] = team.map(_.skills) 

// ✅ flatMap склеює в один плоский список:
val allSkills: List[String] = team.flatMap(_.skills)
// List("Scala", "Akka", "Docker", "Kubernetes")
```

#### Б. Ланцюжок безпечних операцій (контекст опціональності `Option`):
Уявіть два кроки пошуку: знайти користувача за логіном, а потім вичитати його профіль із бази даних (кожен крок може повернути `None`):

```scala
def findUserId(username: String): Option[Int] = ...
def fetchProfile(userId: Int): Option[UserProfile] = ...

// ❌ Звичайний map створює жахливу матрьошку Option[Option[UserProfile]]:
val nestedProfile: Option[Option[UserProfile]] = 
  findUserId("alex").map(id => fetchProfile(id))

// ✅ flatMap автоматично схлопує рівні: якщо хоч один крок None -> весь результат None!
val cleanProfile: Option[UserProfile] = 
  findUserId("alex").flatMap(id => fetchProfile(id))
```
Це закладає фундамент під **Монади** та синтаксис `for-comprehension`, який ми будемо використовувати в усьому курсі.

### 4. За межами трійці: Групування (`groupBy`), проєкції мап (`mapValues`) та сортування (`sortBy`)

У промислових сервісах обробка даних рідко завершується простими `map` та `filter`. Дуже часто перед нами стоїть завдання, аналогічне SQL-запиту з агрегацією:  
`SELECT donor, SUM(amount) FROM donations GROUP BY donor ORDER BY sum DESC LIMIT n`.

У класичному ООП/Java без Streams це вимагало б ручного циклу з `Map<String, Double>` та постійних перевірок `map.containsKey` чи `map.put(..., map.get(...) + amount)`.  
У чистому функціональному підході ми збираємо **декларативний конвеєр трансформації форми даних** (саме так реалізовано аналітику у [Практиці 03: Банка донатів](p03_javish_donation_jar.md)):

```scala
case class Donation(donor: String, amount: Double)

val donations = List(
  Donation("Олена", 500.0),
  Donation("Андрій", 1200.0),
  Donation("Олена", 700.0),
  Donation("Марія", 300.0)
)

val topDonors: List[(String, Double)] = donations
  .groupBy(_.donor)               // 1. Групування: List[Donation] -> Map[String, List[Donation]]
  .view                           // 2. Легковажний View: без зайвого виділення проміжних мап у купі
  .mapValues(_.map(_.amount).sum) // 3. Агрегація значень: Map[String, Double]
  .toList                         // 4. Мапа в список пар-кортежів: List[(String, Double)]
  .sortBy(-_._2)                  // 5. Сортування за сумою спаданням (._2 — другий елемент пари)
  .take(2)                        // 6. Топ-2: List(("Олена", 1200.0), ("Андрій", 1200.0))
```

#### Анатомія трансформації форми даних (Data Flow Trace):

| Крок | Метод | Тип результату | Стан даних на кроці |
| :---: | :--- | :--- | :--- |
| **0** | *Вхід* | `List[Donation]` | 4 сирих факти донатів |
| **1** | `.groupBy(_.donor)` | `Map[String, List[Donation]]` | `"Олена" -> [500, 700]`, `"Андрій" -> [1200]`, `"Марія" -> [300]` |
| **2** | `.view.mapValues(...)` | `MapView[String, Double]` | Значення згорнуті в суми: `"Олена" -> 1200.0`, `"Андрій" -> 1200.0` |
| **3** | `.toList` | `List[(String, Double)]` | Пари `("Олена", 1200.0)`, `("Андрій", 1200.0)`, `("Марія", 300.0)` |
| **4** | `.sortBy(-_._2)` | `List[(String, Double)]` | Відсортовано за спаданням (`-` перед `_._2` перевертає порядок) |
| **5** | `.take(2)` | `List[(String, Double)]` | `List(("Олена", 1200.0), ("Андрій", 1200.0))` |

> 💡 **Чому саме `.view.mapValues`?**  
> У старій Scala 2 метод `mapValues` на мапі був приховано лінивим, що створювало підступні баги з багаторазовим переобчисленням. У Scala 2.13 та Scala 3 мова вимагає писати `.view.mapValues`: цим ви явно кажете компілятору: *«Я створюю легковажну проєкцію без клонування хеш-таблиці перед фінальним зведенням у `.toList`»*.

## 4. Анатомія короля функціонального програмування: `foldLeft`

Що робити, якщо треба порахувати суму чисел, згрупувати об'єкти чи знайти максимум?  
В імперативному стилі заводиться мутабельна змінна `var acc = 0`, яка перезаписується на кожному кроці.  
У ФП для цього існує універсальна операція — **згортка (`foldLeft`)**.

### Метафора «Снігової кулі»
Уявіть снігову кулю, яку котять засніженим схилом:
1. **Початковий стан (Zero / Initial value):** Маленька сніжка в руках (наприклад, `0` або порожній список).
2. **Список елементів:** Сніжинки на траві.
3. **Функція кроку (Step):** Як саме нова сніжинка налипає на кулю `(Куля, Сніжинка) => НоваКуля`.

```scala
val numbers = List(1, 2, 3, 4)

// foldLeft(початкове_значення) { (акумулятор, елемент) => новий_акумулятор }
val sum = numbers.foldLeft(0) { (acc, x) => acc + x }
```

### Трасування роботи `foldLeft(0)(_ + _)`:
| Крок | Вхідний елемент | Акумулятор ДО кроку | Формула | Акумулятор ПІСЛЯ кроку |
| :---: | :---: | :---: | :---: | :---: |
| **Старт** | — | — | — | **`0`** (базове значення) |
| **1** | `1` | `0` | `0 + 1` | `1` |
| **2** | `2` | `1` | `1 + 2` | `3` |
| **3** | `3` | `3` | `3 + 3` | `6` |
| **4** | `4` | `6` | `6 + 4` | **`10`** (фінал) |

---

### 🛡️ Візуалізація Stack Safety: чому `foldLeft` ніколи не впаде з `StackOverflowError`

Для списку `List(1, 2, 3)` зіставте асоціативність та роботу стеку пам'яті:

```text
[foldLeft — ліва асоціативність, хвостова рекурсія O(1) стеку]:
((0 + 1) + 2) + 3
    (1 + 2) + 3
        3 + 3
            6 ──► Стек вільний! Проміжний підсумок обчислюється миттєво.

[foldRight — права асоціативність, накопичення стеку O(N)]:
1 + (2 + (3 + 0)) 
  ▲    ▲    ▲ 
  └────┴────┴──► JVM змушена тримати в пам'яті ВСІ фрейми викликів!
                 Лише дійшовши до кінця (3 + 0), вона починає зворотне додавання.
```

* **Чому це критично для Production:**  
  Якщо у списку 1 000 000 транзакцій, `foldLeft` виконається в константному розмірі стеку за мілісекунди.  
  Натомість `foldRight` накопичить 1 000 000 незавершених викликів і негайно обвалить додаток з **`java.lang.StackOverflowError`**.

---

### 💡 Інженерний інсайт: Усі трансформації — це насправді `foldLeft`!
Будь-яка стандартна операція над колекціями — це лише частковий випадок `foldLeft`:

```scala
// Як реалізовано map через foldLeft:
def myMap[A, B](list: List[A])(f: A => B): List[B] =
  list.foldLeft(List.empty[B]) { (acc, elem) => acc :+ f(elem) }

// Як реалізовано filter через foldLeft:
def myFilter[A](list: List[A])(predicate: A => Boolean): List[A] =
  list.foldLeft(List.empty[A]) { (acc, elem) => 
    if predicate(elem) then acc :+ elem else acc 
  }
```

## 5. Стан як згортка подій (Місток до Event Sourcing)

У розподілених системах стан сервера ніколи не зберігають у мутабельних змінних.  
Замість цього стан системи моделюється як **чиста згортка незмінного журналу подій (Event Log)**:

```
[Подія 1: Створено рахунок] ──┐
[Подія 2: Поповнення +500 ]  ─┼──► foldLeft(Початковий_стан) ──► Баланс: 400 грн
[Подія 3: Списання  -100  ] ──┘
```

Саме за цим принципом працює ігровий рушій нашого наскрізного проєкту [23_runner (Практика 06)](p06_engine_architecture.md):
```scala
// Ігровий світ на 100-му тіку — це результат згортки 100 дій ботів:
val finalState = actionsHistory.foldLeft(initialState) { (state, action) =>
  Engine.nextTick(state, action)
}
```

## 6. Композиція функцій: Трубопровід без проміжних змінних

У класичному коді розробник змушений плодити «локшину» з десятків тимчасових одноразових змінних, у яких легко заплутатися:

```scala
// ❌ Імперативний стиль: шум із тимчасових імен
val rawInput    = "  10000  "
val parsedValue = parseRawInput(rawInput)
val calculated  = calculateTax(parsedValue)
val finalResult = formatReceipt(calculated)
```

У ФП функції є **нерухомими інструментами фабричного конвеєра**. Вони з'єднуються напряму через математичну композицію `andThen`:

```scala
val parseRawInput: String => Int    = str => str.trim.toInt
val calculateTax: Int => Double     = income => income * 0.18
val formatReceipt: Double => String = tax => f"Податок: $tax%.2f грн"

// ✅ Будуємо готовий конвеєр: (A => B) andThen (B => C) andThen (C => D)
val pipeline: String => String = parseRawInput andThen calculateTax andThen formatReceipt

// Пропускаємо сирі дані крізь зафіксований інструмент:
pipeline("  10000  ") // "Податок: 1800.00 грн"
```

Жодних зайвих імен, жодного проміжного стану. Кожна функція залишається ізольованою, легкою для тестування та повторного використання.

## Резюме: Правило трьох секунд

* **Немає індексів — немає багів:** цикли `for/while` замінюються на декларативні пайплайни `filter`, `map`, `fold`.
* **Функція — це звичайне значення:** її можна передавати в аргументи, групувати в колекції та компонувати.
* **`foldLeft` — це ядро обчислень:** будь-який накопичувальний процес (підрахунок грошей, стан гри, аналіз логів) є чистою згорткою без мутацій.

## Контрольні питання для самоперевірки

<details markdown="1">
<summary>1. Чому foldLeft називається саме "Left" і чим він відрізняється від foldRight?</summary>

`foldLeft` починає рух від першого (лівого) елемента списку до останнього. Він є **хвостово-рекурсивним (Tail-Recursive)** і виконується в константному стеку ($O(1)$ пам'яті), тому ніколи не викличе `StackOverflowError`. Натомість `foldRight` розгортається справа наліво і накопичує фрейми у стеку викликів, тому на мільйонних списках він може звалити JVM.
</details>

<details markdown="1">
<summary>2. Як за допомогою filter та map реалізувати підрахунок суми зарплат співробітників відділу QA?</summary>

```scala
val qaBudget = employees
  .filter(_.department == "QA")
  .map(_.salary)
  .sum // або .foldLeft(0.0)(_ + _)
```
Тут жодна проміжна колекція не мутує, код читається як звичайне англійське речення.
</details>

<details markdown="1">
<summary>3. Чому функція, яку передають у reduce/fold при паралельних обчисленнях, має бути асоціативною?</summary>

Асоціативність означає, що $(a + b) + c = a + (b + c)$. Якщо операція асоціативна (як додавання чи множення), список можна розрізати на 16 шматків, обчислити згортку окремо на 16 ядрах процесора у будь-якому порядку і склеїти результати. Якщо операція неасоціативна (як віднімання чи ділення), паралельне обчислення видасть випадковий неправильний результат.
</details>

<details markdown="1">
<summary>4. Що відбувається під капотом у ланцюжку list.groupBy(f).view.mapValues(g)?</summary>

1. `groupBy(f)` розбиває вихідний список на мапу списків `Map[K, List[V]]`, де ключем є результат функції `f`.
2. `.view` відкриває ліниву проєкцію, щоб наступні операції не створювали проміжних копій важкої мапи.
3. `.mapValues(g)` трансформує лише значення (списки), застосовуючи функцію агрегації `g` (наприклад, `.map(_.amount).sum`), перетворюючи мапу списків на підсумкову мапу агрегатів `Map[K, Double]` за один прохід без мутабельних `HashMap`.
</details>
