# Лекція 04. Моделювання предметної області (Type-Driven Design): Алгебраїчні типи даних (ADT), унеможливлення некоректних станів та вичерпний Pattern Matching

> **Декларація курсу.** Академічна доброчесність та авторство матеріалів — у [DISCLAIMER.md](DISCLAIMER.md).  
> **Місток курсу:** У [Лекції 03](03_railway_oriented_programming.md) та на [Практиці 04](p04_transaction_pipeline.md) ми подолали `null` та `Exceptions`, побудувавши платіжний конвеєр на `Either`, де вперше торкнулися каталогу помилок `enum TxError` та смарт-конструкторів. Сьогодні ми підводимо під це системний архітектурний фундамент: **як проєктувати моделі бізнес-домену так, щоб невалідні стани системи було фізично неможливо скомпілювати, а компілятор гарантував 100% вичерпність обробки кожного варіанту?**

### Чому саме «алгебраїчні» типи даних?

Слово «алгебра» тут означає просту арифметику можливих станів програми:

* **Тип-добуток (Product Type / «І» / `case class`):** коли поля існують в об'єкті **одночасно**.  
  Користувач містить ім'я **ТА** вік. Чому це «добуток»? Загальна кількість можливих станів такого об'єкта дорівнює **добутку** значень усіх його полів (Варіанти імені × Варіанти віку). Щоб створити об'єкт, потрібні всі поля разом (`case class` у Scala або `record` у Java).

* **Тип-сума (Sum Type / «АБО» / `enum`):** коли сутність перебуває **лише в одному** взаємовиключному стані.  
  Світлофор горить Червоним (1) **АБО** Жовтим (1) **АБО** Зеленим (1). Загальна кількість станів системи — це **сума**: 1 + 1 + 1 = 3 можливі стани. Варіанти додаються (`enum` у Scala 3 або `sealed interface` у Java 17).

## Питання для розминки

<details markdown="1">
<summary>1. Чому текстовий рядок status: String = "ACTIVE" у доменній моделі — це міна сповільненої дії?</summary>

Тому що компілятор вважає валідним абсолютно будь-який рядок: `"Active"`, `"activ "`, `"COMPLETED"`, `"DELETE FROM users"`. Будь-яка механічна одруківка в коді успішно скомпілюється, але під час виконання призведе до мовчазного збою бізнес-логіки. Статуси мають бути строго типізованими закритими множинами (`enum`), а не довільним текстом.
</details>

<details markdown="1">
<summary>2. Якщо стан замовлення задати кількома прапорцями boolean (наприклад, isPaid, isCancelled, isShipped), яка проблема виникне одразу?</summary>

Будь-які незалежні булеві змінні можна одночасно виставити в `true` (замовлення виявиться і відправленим, і скасованим одночасно!) або всі в `false`. Замість 3 валідних станів ми отримуємо 2 × 2 × 2 = 8 можливих комбінацій, більшість із яких є суперечливими та призводять до збоїв бізнес-логіки. Взаємовиключні стани мають бути вибором «АБО» (`enum`), а не набором незалежних прапорців.
</details>

<details markdown="1">
<summary>3. Що краще: написати 100 тестів на перевірку коректності стану чи спроєктувати типи так, щоб некоректний стан було неможливо скомпілювати?</summary>

Тести перевіряють лише ті сценарії, про які здогадався подумати розробник. Строга система типів гарантує математичну неможливість помилки для 100% випадків. Як сформулював Ярон Мінскі з фінансової компанії Jane Street: **«Зробіть некоректні стани неможливими для представлення (Make illegal states unrepresentable)»**.
</details>

## 1. Архітектурний кейс: «Зомбі-замовлення з трекінг-номером»

**Контекст:** Міжнародна eCommerce-платформа обробляє 100 000 замовлень на добу.  
В імперативному ООП сутності зазвичай моделюють як один гігантський клас з усіма можливими полями:

```java
// Типовий роздутий ООП-клас у стилі Java:
public class Order {
    private String status;           // "PENDING", "SHIPPED", "CANCELLED"
    private String trackingNumber;   // Має бути ТІЛЬКИ для SHIPPED
    private String cancellationReason; // Має бути ТІЛЬКИ для CANCELLED
    private Long refundTransactionId; // Має бути ТІЛЬКИ для CANCELLED
    // ... ще 20 полів та гетери/сетери
}
```

### Що пішло не так:
1. Покупець скасував дороге замовлення на 50 000 $. Оператор техпідтримки викликав `order.setStatus("CANCELLED")` і оформив повернення коштів.
2. Але через збій у паралельному потоці раніше згенерований `trackingNumber` **залишився в об'єкті**.
3. Фоновий складський робот кожні 5 хвилин вичитував із бази всі замовлення з ненульовим трекінг-номером:
   ```java
   if (order.getTrackingNumber() != null) {
       warehouseApi.dispatchPackage(order); // Відвантажити зі складу!
   }
   ```
4. Робот відвантажив клієнту дорогу техніку зі складу, хоча гроші за неї вже повернули на картку покупця.
5. Збитки компанії за вихідні перевищили $200 000.

**У чому корінь проблеми?**  
Клас `Order` дозволяв одночасно існувати взаємовиключним даним: замовлення одночасно мало статус `"CANCELLED"` і реальний `trackingNumber`. Компілятор мовчав, бо типи дозволяли цей абсурд.

## 2. Алгебра типів: Product Types (AND) та Sum Types (OR)

Будь-яку сутність у світі можна скласти з двох базових алгебраїчних операцій над типами:

| Конструкція | Логіка | У коді Scala 3 | Зміст |
| :--- | :--- | :--- | :--- |
| **Product Type** (Тип-добуток) | **«І» (AND)** | `case class` | Властивість А **І** властивість Б |
| **Sum Type** (Тип-сума) | **«АБО» (OR)** | `enum` / `sealed trait` | Варіант А **АБО** Варіант Б |

### 1. Product Type (Тип-добуток / AND)
Коли об'єкт складається з кількох полів одночасно.  
У Scala для цього використовують **`case class`** — спеціальний клас для моделювання незмінних даних (концептуальний аналог `record` у Java). Компілятор автоматично генерує для нього:
* **Незмінні поля** (`val` за замовчуванням).
* **Порівняння за значенням** (`equals`/`hashCode` порівнюють вміст, а не посилання в пам'яті).
* **Метод `copy`** для створення копій зі зміненими полями без мутації оригіналу.
* **Деструктуризацію (розпакування для Pattern Matching):** зворотну дію до конструктора. Можливість «розібрати» готовий об'єкт на складові поля за один крок без ручного виклику гетерів.

```scala
case class GeoPoint(latitude: Double, longitude: Double)

// 1. Конструкція (збираємо поля в об'єкт):
val point = GeoPoint(46.48, 30.72)

// 2. Деструктуризація (розпаковуємо об'єкт назад на окремі змінні):
val GeoPoint(lat, lon) = point 
// Тепер lat = 46.48, lon = 30.72 без жодних point.getLatitude()

// У Pattern Matching це дозволяє витягати поля «на льоту»:
point match
  case GeoPoint(lat, lon) => println(s"Координати: $lat, $lon")
```
#### Інженерний зміст: що насправді дає множення варіантів (N × M)?

Академічні підручники повторюють це як мантру, але рідко пояснюють практичну суть. Для інженера це формула контролю складності:

**1. Небезпека комбінаторного вибуху (State Space Explosion):**  
Кожне нове поле в класі не додає варіанти, а **перемножує** їх:
* Додали в об'єкт 3 прапорці `Boolean` — отримали 2 × 2 × 2 = **8 станів**.
* Додали ще 5 прапорців — уже 2⁸ = **256 станів**.
* Додали `status: String` — отримали **мільярди** потенційних значень.

Чим більше перемножень (N × M), тим більший простір станів, який розробник фізично не здатний покрити тестами чи утримати в голові. Саме в зайвих, непередбачених комбінаціях і ховаються 90% прихованих багів.

**2. Головне правило: коли використовувати `case class`, а коли ні?**  
Формула N × M дає залізобетонний критерій:

* **Поля дійсно незалежні? → Використовуємо `case class` (Product Type).**  
  `GeoPoint(latitude, longitude)` — законний тип-добуток. Широта і довгота не залежать одна від одної. Зміна широти не робить довготу невалідною. Тут множення станів природне й безпечне.
* **Між полями є залежність? → Використовувати `case class` заборонено!**  
  `Order(status, trackingNumber, cancellationReason)` — це архітектурна помилка. Розробник перемножив дані, які є взаємовиключними. У результаті виник неможливий стан `status = "CANCELLED"` разом із `trackingNumber = "1Z999"`, через який система відвантажила скасований товар клієнту вже після повернення коштів.

**Що робити, коли між полями є залежність?**  
Розривати множення і переходити від типу-добутку («І») до **типу-суми («АБО»)**, де кожен стан має лише власні параметри.

### 2. Sum Type (Тип-сума / OR / Coproduct)
Коли сутність може перебувати **лише в одному** із заздалегідь відомих взаємовиключних станів.  
У Scala для цього використовують **`sealed trait`** або сучасний **`enum`**:

* **`sealed trait` (фундамент типізації):**
  * **`trait`** — аналог інтерфейсу в Java (може містити контракти методів і дефолтну поведінку).
  * Модифікатор **`sealed`** («запечатаний») забороняє створювати підтипи за межами поточного файлу. Усі можливі варіанти відомі компілятору заздалегідь.
  * Гарантує **Exhaustiveness Checking** (перевірку на повноту): якщо в конструкції `match` пропустити хоча б один стан, компілятор видасть попередження. Це запобігає аварійним `MatchError` у продакшені.
* **`enum` (лаконічний синтаксис Scala 3):**
  * Першокласна конструкція для швидкого створення типів-сум без зайвого шаблонного коду.
  * На відміну від `enum` у Java (де всі елементи є фіксованими константами), у Scala 3 варіанти можуть містити власні поля й параметри (повноцінні типи-добутки всередині типу-суми).

```scala
enum PaymentMethod:
  case Cash                                    // простий синглтон без полів (case object)
  case CreditCard(number: String, cvv: String) // варіант із даними (Product Type / case class)
  case ApplePay(token: String)
```

> 💡 **Що робить `Cash` синглтоном?**
> * **Синтаксис без дужок `()` ➔ `case object`:** якщо варіант не має полів, компілятор Scala 3 створює для нього не клас, а **синглтон-об'єкт**.
> * **Гарантія JVM:** створюється рівно один екземпляр у пам'яті (статичне поле), ініціалізований завантажувачем класів (ClassLoader).
> * **Zero-GC та продуктивність:** скільки б мільйонів транзакцій готівкою не оброблялося, `PaymentMethod.Cash` завжди посилається на один і той самий об'єкт. Порівняння відбувається миттєво за посиланням, а збирач сміття (GC) не створює оверхеду.
> * **Контраст:** якщо варіант містить параметри в дужках `(...)` (як `CreditCard`), компілятор генерує повноцінний `case class`, який виділяє пам'ять під новий об'єкт для кожного виклику.

<details markdown="1">
<summary>Що під капотом? (Цукор над класичним <code>sealed trait</code> та <code>case object</code>)</summary>

`enum` у Scala 3 — це чистий **синтаксичний цукор**. Компілятор автоматично розгортає його в класичний патерн:

```scala
sealed trait PaymentMethod
object PaymentMethod:
  // 1. Варіант без полів -> синглтон:
  case object Cash extends PaymentMethod

  // 2. Варіанти з полями -> класи з новими інстансами під кожен виклик:
  case class CreditCard(number: String, cvv: String) extends PaymentMethod
  case class ApplePay(token: String) extends PaymentMethod
```
*(Аналог у Java 17+: `sealed interface PaymentMethod permits Cash, CreditCard, ApplePay`).*
</details>

* **Чому це сума?**  
  Оплата може бути здійснена АБО готівкою (1 варіант), АБО карткою (M варіантів), АБО Apple Pay (K варіантів). Загальна множина можливих способів є їхньою сумою:  
  **Кількість способів оплати = Варіанти Cash + Варіанти CreditCard + Варіанти ApplePay** (або 1 + M + K).

* **Навіщо `sealed` у предметній області (Domain Modeling)?**  
  * **Закрита множина бізнес-станів:** У реальному бізнесі способи оплати строго обмежені. `sealed` гарантує, що сторонній код не зможе підкинути невідомий системі варіант оплати.
  * **Компілятор як бізнес-аудитор:** Якщо завтра додати новий стан `case Crypto(...)`, компілятор попередить про всі місця у системі (комісії, фіскалізація, повернення), де його забули обробити. Людський фактор зводиться до нуля.
  * **Відмінність від ООП-інтерфейсу:** В ООП інтерфейс відкритий (новий клас додати легко, але складно додати нову операцію). У ФП доменні стани замкнені (`sealed`), а операції над ними винесені в чисті бізнес-функції.

## 3. «Make Illegal States Unrepresentable» на практиці

Перепишемо бізнес-модель замовлення за правилами строгого Type-Driven Design.  
Замість одного роздутого класу створюємо **тип-суму (Sum Type)**:

```scala
// Тепер кожен стан має ТІЛЬКИ ті дані, які йому належать:
enum Order:
  case Pending(createdAt: Long)
  case Shipped(trackingNumber: String, dispatchedAt: Long)
  case Cancelled(reason: String, refundTransactionId: Long)
```

### Чому ця архітектура бездоганна:
1. **Неможливість збою:** Ви фізично не можете створити об'єкт `Order.Cancelled`, у якого є `trackingNumber`. Такого поля у нього просто **не існує в пам'яті**.
2. **Нуль `null`:** Нам більше не потрібні поля з `null` чи надлишкові `Option` для кожного параметру.
3. **Чесність перед базою даних:** Стан системи завжди гарантовано консистентний.

---

### Паттерн «Розумний конструктор» (Smart Constructor)
ADT чудово захищає від *структурно* неможливих станів. Але як захистити систему від некоректних *значень* усередині валідних полів?  
Наприклад, якщо ми створимо `case class Email(value: String)`, ніхто не завадить передати туди `Email("not-an-email")`, і ми знову отримаємо збій у рантаймі під час відправки пошти!

**Рішення:** приватний первинний конструктор та фабричний метод у компаньйон-об'єкті, що повертає `Either`:

```scala
// 1. Конструктор приватний: ніхто ззовні не може викликати new Email(...)
final case class Email private (value: String)

object Email:
  // 2. Єдиний шлях створення — перевірений шлюз, що повертає Either:
  def fromString(raw: String): Either[String, Email] =
    val trimmed = raw.trim
    if trimmed.contains("@") && trimmed.split("@").length == 2 then
      Right(new Email(trimmed))
    else
      Left(s"Некоректний формат email: '${raw}'")

// Використання:
val badEmail  = Email.fromString("broken-string") // Left(Некоректний формат email...)
val goodEmail = Email.fromString("user@onu.edu.ua") // Right(Email(user@onu.edu.ua))
```
Це ідеальний шлюб між **Railway-Oriented Programming (Either з Лекції 03)** та **Type-Driven Design**: якщо функція приймає `Email`, їй більше непотрібно валідувати рядок — валідність гарантована самим фактом існування типу!

### Рекурсивні типи даних (Recursive ADTs): Анатомія списку

В університетських курсах нас часто вчать: **«уникайте рекурсії у продакшені»**, бо розгортання стеку викликів швидко призводить до переповнення пам'яті (`StackOverflowError`). Але світ JVM та мовних компіляторів не стоїть на місці: оптимізації хвостової рекурсії дозволяють писати чистий математичний код, який безпечно працює у навантажених системах навіть на глибині понад 100 000 викликів без жодного зростання стеку пам'яті.

Алгебраїчні типи даних можуть також посилатися на самих себе. Класичний незмінний `List` у Scala — це не магія мови, а звичайний рекурсивний Sum Type, який кожен може написати за 5 хвилин:

```scala
// Наш власний однозв'язний список:
// +A — коваріантність (з Лекції 03): якщо Dog <: Animal, то й MyList[Dog] <: MyList[Animal]
enum MyList[+A]:
  case Nil                                 // Порожній список (термінальний вузол)
  case Cons(head: A, tail: MyList[A])      // Рекурсивна ланка: елемент + хвіст (у стандартному List це клас ::)

// Створення списку 1 -> 2 -> 3 -> Nil:
import MyList._
val numbers = Cons(1, Cons(2, Cons(3, Nil))) // аналог стандартного запису: 1 :: 2 :: 3 :: Nil

import scala.annotation.tailrec

// Хвостово-рекурсивний підрахунок суми (Stack-Safe: O(1) стеку, оптимізується компілятором у цикл):
def sum(list: MyList[Int]): Int =
  // @tailrec наказує компілятору перевірити оптимізацію в цикл: якщо рекурсія НЕ хвостова — буде помилка компіляції
  @tailrec
  def loop(curr: MyList[Int], acc: Int): Int = curr match
    case MyList.Nil         => acc
    case MyList.Cons(x, xs) => loop(xs, acc + x) // ХВОСТОВИЙ ВИКЛИК: loop — остання дія, нічого після неї!

  loop(list, 0)
```

#### Покрокове виконання для списку 1 -> 2 -> 3 -> Nil:

```text
Крок 1: loop(Cons(1, Cons(2, Cons(3, Nil))), acc = 0)
        curr = Cons(1, ...), новий acc = 0 + 1 = 1

Крок 2: loop(Cons(2, Cons(3, Nil)), acc = 1)
        curr = Cons(2, ...), новий acc = 1 + 2 = 3

Крок 3: loop(Cons(3, Nil), acc = 3)
        curr = Cons(3, Nil), новий acc = 3 + 3 = 6

Крок 4: loop(Nil, acc = 6)
        curr = Nil, спрацьовує базовий випадок → повертаємо 6
```

#### Що саме робить виклик «хвостовим» (Tail Call)?

Хвостовим виклик робить **його положення в черзі операцій** — те, **хто виконує найостаннішу дію**:

##### 1. НЕ-хвостовий антиприклад (потрібен стек пам'яті):
```scala
case MyList.Cons(x, xs) => x + loop(xs)
```
1. Спочатку викликається `loop(xs)`.
2. Поточна функція **завмирає і чекає**, поки рекурсія поверне відповідь.
3. І лише **після повернення** виконує останню дію: додає `x + результат`.

> **Чому це не хвіст:** Остання дія тут — **додавання `+`**, а не виклик функції. JVM зобов'язана тримати старий фрейм у стеку, бо їй ще треба пам'ятати число `x`. На 100 000 елементів це гарантований збій **`StackOverflowError`**.

##### 2. Хвостовий виклик (Tail Call):
```scala
case MyList.Cons(x, xs) => loop(xs, acc + x)
```
1. **Спочатку** обчислюються аргументи: `acc + x` (наприклад, 0 + 1 = 1).
2. Сам виклик `loop(...)` є **фінальною дією**. Після нього над результатом **не виконується жодної операції** — що повернув `loop`, те функція й віддає нагору.

> **Магія компілятора:** Оскільки поточному фрейму більше нічого робити, компілятор просто **перезаписує змінні поточного фрейму** новими аргументами (`curr = xs`, `acc = acc + x`) і стрибає на початок функції звичайною інструкцією `goto`.

> **Просте правило для перевірки:**  
> Виклик є хвостовим, якщо після повернення з рекурсивної функції ви **не робите з отриманим значенням взагалі нічого** (ні `+`, ні `::`, ні `map`). Ви просто одразу повертаєте результат виклику як є.

#### Порівняння: Scala з `@tailrec` проти звичного циклу `while` у Java

Scala-компілятор автоматично перетворює декларативну хвостову рекурсію на звичайний імперативний плоский цикл `while` у байткоді:

```scala
// 1. Що ми пишемо у Scala (декларативно, без змінних var):
@tailrec
def loop(curr: MyList[Int], acc: Int): Int = curr match
  case MyList.Nil         => acc
  case MyList.Cons(x, xs) => loop(xs, acc + x)
```

```java
// 2. У що це компілюється під капотом (еквівалент на звичній Java):
public static int sum(MyList<Integer> list) {
    MyList<Integer> curr = list;
    int acc = 0;
    while (curr instanceof MyList.Cons<Integer> cons) {
        acc += cons.head(); // acc + x
        curr = cons.tail(); // перехід до залишку xs
    }
    return acc;             // Nil -> повертаємо acc
}
```

> **Головний висновок для інженера:**  
> Ми пишемо чистий функціональний код без мутабельних змінних (`var`), а компілятор завдяки `@tailrec` генерує настільки ж швидкий і стек-безпечний байткод, як звичайний цикл `while` у Java з O(1) пам'яті стеку.

## 5. Вичерпний Pattern Matching (Exhaustiveness Checking)

Коли стан змодельовано через ADT, класичний оператор `switch` із Java стає непотрібним. Ми використовуємо **Pattern Matching**:

```scala
def processOrder(order: Order): Unit = order match
  case Order.Pending(time) =>
    println(s"Очікує оплати від $time")
    
  case Order.Shipped(trackId, _) =>
    notifyCourier(trackId)
    
  case Order.Cancelled(reason, refundId) =>
    refundMoney(refundId)
```

### Компілятор як безкоштовний QA-інженер
Уявіть, що через пів року бізнес додав новий статус замовлення:  
`case ReturnedToWarehouse(defectDescription: String)`.

Якщо ви забудете обробити його десь у глибині 100 000 рядків коду, компілятор Scala 3 **не скомпілює проєкт** і видасть попередження:

```text
[warn] match may not be exhaustive!
[warn] It would fail on the following input: Order.ReturnedToWarehouse(_)
```

**Це кінець епохи непередбачуваних рантайм-помилок:**  
Вам більше не потрібно шукати всі виклики через текстовий `grep` по проєкту — компілятор сам перерахує точні номери рядків у всіх файлах, де потрібно дописати обробку нового бізнес-стану.

---

### Пастка лінивого розробника: Чому дефолтний `case _` — це міна сповільненої дії

Початківці часто полюбляють ставити `case _ => ...` наприкінці кожного `match`, аби швидше задовольнити компілятор.  
В індустріальному коді це **один із найнебезпечніших антипатернів**.

#### Як виникає спокуса поставити `case _`?

Уявіть платіжну систему з трьома базовими статусами:

```scala
enum PaymentStatus:
  case Pending
  case Authorized
  case Declined
```

Розробник пише метод виплати, але його цікавлять лише успіх і відмова:

```scala
def processPayout(status: PaymentStatus): Unit = status match
  case PaymentStatus.Authorized => releaseFundsToMerchant()
  case PaymentStatus.Declined   => notifyCustomer()
```

Компілятор Scala миттєво б'є на сполох і видає попередження:

```text
[warn] match may not be exhaustive!
[warn] It would fail on the following input: PaymentStatus.Pending
```

І тут початківець зі старої звички з Java (де в `switch` завжди ставили `default`) або просто з бажання «прибрати жовте підкреслення в IDE» ставить «швидкий фікс»:

```scala
def processPayout(status: PaymentStatus): Unit = status match
  case PaymentStatus.Authorized => releaseFundsToMerchant()
  case PaymentStatus.Declined   => notifyCustomer()
  case _                        => logWarning("Невідомий статус, пропустимо") // Аби компілятор замовк!
```

Код скомпілювався, задача закрита. Але закладено міну сповільненої дії.

#### Що стається при розвитку бізнесу?

Через пів року відділ безпеки банку додає новий статус для блокування шахраїв:

```scala
enum PaymentStatus:
  case Pending
  case Authorized
  case Declined
  case FraudSuspicious // Новий статус: підозра на шахрайство!
```

Що станеться з двома варіантами коду:

1. **З дефолтним `case _`:**  
   Компілятор **мовчки збирає проєкт**. Підозріла транзакція потрапляє в `case _`, фінмоніторинг не отримує сигналу тривоги, і компанія зазнає збитків. Помилка виявиться вже у продакшені.
2. **БЕЗ дефолтного `case _`:**  
   Компілятор зупинить збірку та вкаже на пропущений `FraudSuspicious`. Він буквально бере інженера за руку й вимагає явно визначити бізнес-поведінку: заблокувати рахунок, сповістити службу безпеки чи відправити на перевірку.

> **Золоте правило інженера:**  
> Пишіть дефолтний `case _` тільки тоді, коли ви **свідомо** хочете ігнорувати абсолютно всі майбутні зміни типу. В інших 95% випадків перераховуйте всі гілки явно!

## 6. Pattern Guards (Охоронні умови) та деструктуризація

Pattern Matching уміє заглядати глибоко всередину вкладених структур і перевіряти складні логічні умови прямо в заголовку `case`.

### Приклад: Валідатор сумісності ПК (CPU, материнська плата, пам'ять, корпус і TDP)

Уявіть конфігуратор робочих станцій. Потрібно перевірити фізичну та термічну сумісність процесора, материнської плати, оперативної пам'яті та корпусу:

```scala
enum CpuArch:
  case X86, Arm, RiscV

enum FormFactor:
  case ATX, MicroATX, MiniITX

case class Cpu(model: String, arch: CpuArch, tdpWatts: Int)
case class Motherboard(socket: String, formFactor: FormFactor, memorySlots: Int)
case class Case(supportedFormFactors: List[FormFactor], maxTdpWatts: Int, isSilent: Boolean)

// Комп'ютер у зборі (деструктурується прямо в match):
case class ComputerBuild(
  cpu: Cpu,
  motherboard: Motherboard,
  ramGb: Int,
  chassis: Case
)

enum BuildVerdict:
  case Approved(profile: String)
  case ThermalRisk(warning: String)
  case IncompatibleSize(reason: String)

def validateBuild(build: ComputerBuild): BuildVerdict = build match
  // 1. Деструктуризація + Guard: перегрів у компактному корпусі (TDP процесора > ліміту шасі)
  case ComputerBuild(Cpu(model, _, tdp), _, _, chassis) if tdp > chassis.maxTdpWatts =>
    BuildVerdict.ThermalRisk(
      s"Процесор $model виділяє ${tdp}W, але корпус розраховано максимум на ${chassis.maxTdpWatts}W"
    )

  // 2. Деструктуризація + Guard: материнська плата фізично не поміщається в корпус
  case ComputerBuild(_, Motherboard(_, mbForm, _), _, chassis) if !chassis.supportedFormFactors.contains(mbForm) =>
    BuildVerdict.IncompatibleSize(
      s"Форм-фактор плати $mbForm не підтримується вибраним корпусом"
    )

  // 3. Зіставлення за внутрішнім enum + Guard: ARM-сервер з великим обсягом пам'яті (>= 128 GB)
  case ComputerBuild(Cpu(model, CpuArch.Arm, _), _, ram, _) if ram >= 128 =>
    BuildVerdict.Approved(s"Енергоефективний ARM-сервер ($model, ${ram}GB RAM)")

  // 4. Глибока перевірка константи: тихий корпус і холодний процесор (TDP <= 65W)
  case ComputerBuild(Cpu(model, _, tdp), _, _, Case(_, _, true)) if tdp <= 65 =>
    BuildVerdict.Approved(s"Тиха домашня/офісна станція ($model, ${tdp}W)")

  // 5. Усі інші сумісні конфігурації
  case ComputerBuild(cpu, mb, ram, _) =>
    BuildVerdict.Approved(s"Стандартний ПК (${cpu.model}, ${mb.formFactor}, ${ram}GB RAM)")
```

## 7. Куточок архітектора: Моделювання бізнес-процесів як скінченних автоматів (State Machine / FSM)

ADT — це не просто пасивні контейнери для даних. Це **математичний фундамент для моделювання життєвого циклу бізнес-процесів**.

У надійних розподілених системах перехід між станами моделюють як чисту детерміновану функцію:

```scala
transition: (State, Command) => Either[DomainError, State]
```

### Приклад: Управління життєвим циклом замовлення

```scala
// 1. Команди (події), що надходять у систему:
enum OrderCommand:
  case Ship(trackingNumber: String)
  case Cancel(reason: String)
  case Deliver

// 2. Чистий перехід станів (State Transition FSM):
def handleCommand(order: Order, cmd: OrderCommand): Either[String, Order] = 
  (order, cmd) match
    // Валідний перехід: Pending -> Shipped
    case (Order.Pending(_), OrderCommand.Ship(track)) =>
      Right(Order.Shipped(track, System.currentTimeMillis()))

    // Валідний перехід: Pending -> Cancelled
    case (Order.Pending(_), OrderCommand.Cancel(reason)) =>
      Right(Order.Cancelled(reason, refundTransactionId = 987654L))

    // Спроба відправити вже скасоване замовлення — неможливий перехід!
    case (Order.Cancelled(_, _), OrderCommand.Ship(_)) =>
      Left("Помилка домену: неможливо відправити скасоване замовлення!")

    // Будь-яка інша заборонена бізнес-правилами комбінація:
    case (current, illegalCmd) =>
      Left(s"Недопустима дія $illegalCmd для поточного стану $current!")
```

### Чому цей патерн фундаментальний:
* **Неможливість збою гонитви (Race Conditions):** Функція переходу станів є чистою. Якщо два запити прийдуть одночасно, один із них гарантовано поверне зрозумілий `Left`.
* **Інкапсуляція бізнес-правил:** Усі дозволені та заборонені переходи описані в одній матриці `match`, а не розкидані по 10 різних сервісах.
* **Місток до Event Sourcing та Akka/Pekko:** Саме за таким принципом функціонують розподілені актори, які ми будемо створювати в блоці реактивних систем!

## Резюме: Правило трьох секунд

* **Моделюйте бізнес-домен через ADT:** Комбінуйте `case class` (AND) та `enum` (OR).
* **Make Illegal States Unrepresentable:** Не зберігайте невалідні комбінації даних, які потім доведеться ловити валідаторами.
* **Довіряйте компілятору:** Вичерпний Pattern Matching гарантує, що при розширенні системи жоден бізнес-сценарій не буде забутий.

## Контрольні питання для самоперевірки

<details markdown="1">
<summary>1. Чому при моделюванні через sealed trait або enum усі підтипи мають бути оголошені в одному файлі?</summary>

Ключове слово `sealed` ("запечатаний") забороняє розширювати ієрархію за межами поточного файлу вихідного коду. Тільки за цієї умови компілятор знає **повний і закритий перелік усіх можливих нащадків** і може гарантувати 100% вичерпність перевірки (Exhaustiveness Check) у `match`.
</details>

<details markdown="1">
<summary>2. У чому архітектурна небезпека використання `case _ =>` (Default Wildcard) у Pattern Matching для бізнес-сутностей?</summary>

Сліпий `case _ =>` "заглушає" діагностику компілятора. Якщо через рік у систему додадуть новий важливий стан (наприклад, `Order.FraudSuspicion`), компілятор промовчить, і цей критичний випадок тихо провалиться в дефолтну гілку `case _`, спричинивши непередбачувану поведінку. Намагайтеся перераховувати всі стани явно!
</details>

<details markdown="1">
<summary>3. Скільки можливих станів має тип Pair[Boolean, Option[Boolean]]?</summary>

Порахуємо за правилами алгебри типів:
* `Boolean` має 2 стани (`true`, `false`).
* `Option[Boolean]` — це тип-сума: `None` (1 варіант) або `Some(Boolean)` (2 варіанти). Разом: 1 + 2 = 3 стани.
* `Pair` — це тип-добуток (Product Type): Кількість станів Boolean × Кількість станів Option[Boolean] = 2 × 3 = **6** унікальних станів.
</details>
