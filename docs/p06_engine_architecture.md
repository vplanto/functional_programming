## Експрес-опитування та розминка

<details markdown="1">
<summary>1. Чому наявність циклу while та мутабельних змінних var усередині Engine.scala — це виправданий компроміс, а не архітектурна помилка?</summary>

Тому що `Engine.run()` — це **імперативна оболонка (`Imperative Shell`)** на межі побічних ефектів: на кожному тіку вона заміряє фізичний час (`System.nanoTime()`), контролює таймаут виклику бота через `Future`, читає клавіатуру в режимі `--step` і пише в консоль. Усі змінні `var` та мутабельні буфери (`Queue`, `ListBuffer`) є **суворо локальними всередині методу `run()`** — жоден інший потік не має до них доступу, а бот отримує на вхід незмінний знімок `Observation` і повертає чисту дію `Action`.
</details>

<details markdown="1">
<summary>2. Чому методи переходу між смугами повертають Option[Lane], а не кидають виняток при виході за край тунелю?</summary>

Кидання винятку (`throw new OutOfBoundsException`) ламає функціональну чистоту, порушує локальність потоку керування та вимагає побудови стек-трейсу в JVM. Тип `Option[Lane]` робить поведінку **явною на рівні типів**: на крайній лівій смузі лівого сусіда не існує (`None`), а рушій обробляє межі тунелю через `hero.lane.left.getOrElse(hero.lane)`.
</details>

<details markdown="1">
<summary>3. Що станеться, якщо бот почне зберігати історію попередніх дій у внутрішньому полі var myHistory: List[Action]?</summary>

Бот втратить властивість **детермінованості та паралельної безпеки (Thread-Safety)**. Його більше не можна буде безпечно перезапустити з того самого сіда, паралелити чи використовувати в розподілених акторах. Увесь необхідний контекст бот уже отримує у незмінному `Observation`.
</details>

## 1. Архітектурний кейс: Збій каналу керування на випробуваннях Fly-by-Wire

У 1990-х роках під час тестування потрійної комп'ютерної системи управління авіалайнера виник збій: три незалежні обчислювальні канали одночасно оцінювали кут нахилу літака.

Один із модулів використовував «розумну» адаптивну фільтрацію з внутрішнім накопиченням історії помилок. На 14-й хвилині польоту через неочікувану турбулентність внутрішній стан цього алгоритму розійшовся з реальною фізикою, і він почав вимагати різкого пікірування.

**Що врятувало літак?**  
Два інші канали були **повністю stateless (безстановими)**: вони обчислювали реакцію виключно на основі поточного пакета датчиків. **Мажоритарний арбітр (2 проти 1)** заблокував небезпечну команду та безпечно посадив літак.

> **Мораль для інженера:**  
> Спільний змінний стан та прихована внутрішня пам'ять в алгоритмах управління — це джерело аварій у критичних системах. Архітектура [23_runner](https://github.com/vplanto/functional_programming/tree/main/23_runner) будується за цим самим авіаційним принципом.

## 2. «Функціональне ядро, імперативна оболонка» (Core vs Shell)

Проєкт демонструє фундаментальний гібридний баланс сучасної інженерії на Scala:

```
┌──────────────────────────────────────────────────────────┐
│              ІМПЕРАТИВНА ОБОЛОНКА (Engine.scala)          │
│  var hero, var tick, while (hero.alive && tick < max)    │
│  Ізольований state-holder, замір наносекунд, SLA budget  │
│                                                          │
│     ┌──────────────────────────────────────────────┐     │
│     │        ЧИСТЕ ЯДРО (domain.scala)              │     │
│     │  Lane, Height, Stance, Action, TunnelSlice   │     │
│     │  HeroState, Observation (Незмінні case-класи)│     │
│     │                                              │     │
│     │   decide: Observation => Action              │     │
│     │   (Чиста, математично детермінована функція) │     │
│     └──────────────────────────────────────────────┘     │
└──────────────────────────────────────────────────────────┘
```

### Чому в Engine допустимий `var`:
1. **Локальна ізоляція стану (Stack Confinement):** Змінні `var hero`, `var tick`, черга зрізів `Queue` та журнал `ListBuffer` створені всередині одного методу `run()`. До них не має доступу жоден зовнішній об'єкт чи сусідній потік, тому стан гонитви (Race Condition) тут неможливий.
2. **Концентрація всіх побічних ефектів в одному місці:** Саме `Engine.run()` працює з нечистим світом — системним таймером `System.nanoTime()`, контролем таймаутів (`Future` / `Await.result`), вводом/виводом у термінал (`println`, `StdIn.readLine()`). Замість того щоб розмазувати ці ефекти по коду, вони зібрані в одному імперативному циклі.
3. **Чистий зовнішній контракт:** Назовні мутабельність не просочується — бот працює виключно з незмінним `Observation`, а сам `engine.run()` повертає незмінний підсумок забігу `RunSummary`.

## 3. Доменний дизайн у `domain.scala`: Алгебра типів

Домен проєкту використовує виразну силу системи типів Scala 3:

### А. Моделювання простору через закриті `enum`
```scala
enum Lane:
  case Left, Center, Right

  def left: Option[Lane] = this match
    case Right  => Some(Center)
    case Center => Some(Left)
    case Left   => None

  def right: Option[Lane] = this match
    case Left   => Some(Center)
    case Center => Some(Right)
    case Right  => None
```
* **Exhaustiveness checking:** Компілятор перевіряє, що у виразі `match` розглянуто всі можливі смуги.
* **Чесні переходи через `Option`:** Замість магічних чисел `-1` чи помилок, рушій безпечно виражає межі:
  ```scala
  val nextLane = action match
    case Action.MoveLeft  => hero.lane.left.getOrElse(hero.lane)
    case Action.MoveRight => hero.lane.right.getOrElse(hero.lane)
    case _                => hero.lane
  ```

### Б. Модель поперечного зрізу тунелю (матриця 3x3) та фізика стійок

Кожен метр тунелю моделюється як поперечний переріз `TunnelSlice` розміром **3 смуги (`Lane`) × 3 рівні висоти (`Height`) = 9 комірок**:

```
              [ Lane.Left ]   [ Lane.Center ]   [ Lane.Right ]
Height.High (2)    .               [#]                $10       <-- зона стрибка (Jumping)
Height.Mid  (1)    .               (@.@)               .        <-- рівень грудей/голови (Running)
Height.Low  (0)   [#]              (@.@)               .        <-- рівень землі (Running / Ducking)
```

У коді [domain.scala](https://github.com/vplanto/functional_programming/blob/main/23_runner/src/main/scala/runner/domain.scala) зріз реалізовано як незмінне відображення `Map[(Lane, Height), CellItem]`:

```scala
enum Height(val level: Int):
  case Low  extends Height(0) // рівень землі
  case Mid  extends Height(1) // рівень очей / грудей
  case High extends Height(2) // рівень стелі

enum Stance:
  case Running  // займає ОДНОЧАСНО дві комірки: Low (0) та Mid (1)
  case Jumping  // відірвався від землі: займає лише High (2)
  case Ducking  // пригнувся: займає лише Low (0)

enum CellItem:
  case Empty
  case Obstacle
  case Coin(value: Int)

case class TunnelSlice(cells: Map[(Lane, Height), CellItem]):
  def itemAt(lane: Lane, height: Height): CellItem =
    cells.getOrElse((lane, height), CellItem.Empty)

  def hasObstacleAt(lane: Lane, height: Height): Boolean =
    itemAt(lane, height) match
      case CellItem.Obstacle => true
      case _                 => false

  def coinAt(lane: Lane, height: Height): Option[Int] =
    itemAt(lane, height) match
      case CellItem.Coin(v) => Some(v)
      case _                => None
```

**Ключові інваріанти геометрії зрізу (як `Engine` перевіряє зіткнення та монети):**
* **`Stance.Running` займає дві висоти (`Low` + `Mid`):** герой у звичайному бігу збирає монети одночасно з рівнів `0` і `1`, але гине від перешкоди як на землі (`Low`), так і на рівні грудей (`Mid`).
* **`Stance.Ducking` займає лише `Low`:** дозволяє прослизнути під перешкодою на рівні грудей (`Mid`), але не рятує від бар'єра на землі (`Low`).
* **`Stance.Jumping` займає лише `High`:** дозволяє перестрибнути перешкоди на рівнях `Low` і `Mid` (навіть якщо вони стоять одночасно), але призводить до удару об стелю, якщо у комірці `High` є балка.
* **Тотальність функції `itemAt`:** завдяки `cells.getOrElse((lane, height), CellItem.Empty)` зріз є повною (total) функцією `(Lane, Height) => CellItem` — навіть якщо в `Map` передано лише непорожні клітинки, запит до будь-якої з 9 координат ніколи не кине `NoSuchElementException`.

## 4. Таксономія MISD та Мажоритарний Арбітр (`MajorityBot`)

Концепція **MISD (Multiple Instruction, Single Data)** полягає в тому, що **один незмінний об'єкт `Observation`** одночасно передається різним незалежним алгоритмам:

```scala
override def decide(observation: Observation): Action =
  // 1. Паралельне опитування незалежних ботів (MISD)
  val votes: List[Action] = bots.map(_.decide(observation))

  // 2. Функціональне групування та підрахунок голосів
  val counts: Map[Action, Int] = 
    votes.groupBy(identity).view.mapValues(_.size).toMap

  // 3. Знаходження лідера голосування
  val (winnerAction, maxVotes) = counts.maxBy(_._2)

  // 4. Мажоритарний кворум (2 з 3 або 3 з 3)
  if maxVotes >= 2 then winnerAction
  else votes.headOption.getOrElse(Action.KeepRunning)
```

### Як працює підрахунок голосів під капотом (Покрокове трасування)
Уявімо, що три наші боти повернули такі дії: `List(Action.Jump, Action.Jump, Action.MoveLeft)`.

* **Крок 1. `votes.groupBy(identity)`** — групує однакові дії у кошики:
  `Map(Jump -> List(Jump, Jump), MoveLeft -> List(MoveLeft))`
* **Крок 2. `view.mapValues(_.size).toMap`** — ліниво замінює списки на їхню довжину (кількість голосів):
  `Map(Jump -> 2, MoveLeft -> 1)`
* **Крок 3. `counts.maxBy(_._2)`** — знаходить пару з найбільшим значенням:
  `(Jump, 2)`
* **Крок 4. Мажоритарний кворум (`2 >= 2`):** дія `Jump` перемагає більшістю голосів!

### Розбір стартового шаблону `MajorityBot`

Погляньте на повний код стартового файлу [`MajorityBot.scala`](https://github.com/vplanto/functional_programming/blob/main/23_runner/src/main/scala/runner/bots/MajorityBot.scala):

```scala
class MajorityBot(val bots: List[CyberBot]) extends CyberBot:

  def this(seed: Long = 2026L) = this(List(
    new GreedyBot(seed + 101L),
    new ReflexBot(seed + 202L),
    new StrategicBot(seed + 303L)
  ))

  override def decide(observation: Observation): Action =
    val votes = bots.map(_.decide(observation))
    val grouped = votes.groupBy(identity).view.mapValues(_.size).toMap
    val (winnerAction, maxVotes) = grouped.maxBy(_._2)

    if maxVotes >= 2 then
      winnerAction
    else
      votes.headOption.getOrElse(Action.KeepRunning)
```

<details markdown="1">
<summary>Питання до аудиторії: що піде не так, якщо залишити цей шаблон та метод decide без змін?</summary>

У базовій реалізації закладено **дві інженерні пастки**, які потрібно виправити у фінальному проєкті:

1. **Нічия (`1 : 1 : 1`) та порядок у списку `bots`:**  
   Якщо всі три боти запропонували різні дії (`maxVotes == 1`), спрацьовує гілка `else votes.headOption.getOrElse(Action.KeepRunning)`:
   * `votes.headOption` бере **перший елемент списку `votes`**, тобто голос першого бота у списку `bots` (а `.getOrElse(Action.KeepRunning)` є лише синтаксичною страховкою на випадок, якби `MajorityBot` створили з порожнім списком `bots = Nil`).
   * Оскільки у конструкторі першим стоїть `new GreedyBot(...)`, за будь-якої розбіжності думок (`1 : 1 : 1`) `votes.headOption` повертає `Some(дія_GreedyBot)`. Тобто у спірній ситуації вирішальний голос отримує жадібний збирач монет, який ігнорує перешкоди, а не `ReflexBot`.
2. **Відсутність права вето безпеки (Safety Veto):**  
   Навіть за мажоритарної більшості (`2 проти 1`), якщо на поточній смузі на наступному зрізі лежить монета або перешкода, яку не бачить `GreedyBot`, він може проголосувати за небезпечну дію (наприклад, залишитись на смузі через `KeepRunning` або стрибнути за монетою у стелю). Якщо його випадково підтримає ще один бот, кворум `2 з 3` проігнорує голос `ReflexBot` і спрямує героя в перешкоду.  
   **Як правильно:** арбітр має спочатку відсіяти смертельні дії через фільтр безпеки `ReflexBot` (право вето на дії, що ведуть до гарантованого зіткнення на найближчому зрізі), і лише серед безпечних кандидатів обирати переможця голосування.
</details>

## 5. Типові архітектурні помилки при реалізації автопілота

Під час розробки автопілота найчастіше виникають три інженерні проблеми:

```
   ┌─────────────────────────────────────────────────────────────┐
   │                ТИПОВІ ПОМИЛКИ ПРОЄКТУВАННЯ                  │
   ├──────────────────────────────┬──────────────────────────────┤
   │ 1. Мутабельний стан (Stateful)│ Додавання `var` у клас бота │
   │ 2. Часова зв'язність         │ Непрохідність зв'язки N->N+1 │
   │ 3. Експоненційний таймаут    │ Повний перебір O(N) без відсіч│
   └──────────────────────────────┴──────────────────────────────┘
```

### Помилка 1: Збереження внутрішнього стану (Stateful Bot)
* **Симптом:** Додавання поля `var previousAction: Action` або `var jumpsCount: Int` у клас бота.
* **Чому це глухий кут:** Бот має бути **чистою функцією**. Весь контекст уже присутній у `observation.hero` (дистанція, поточна смуга, стійка `stance`, рахунок). Бот із внутрішнім станом стає непередбачуваним при повторному тестуванні чи зміні порядку опитування в ансамблі.

### Помилка 2: Ігнорування часової зв'язності зрізів (`t+1 -> t+2`)
* **Симптом:** Генератор рівнів [LevelGenerator.scala](https://github.com/vplanto/functional_programming/blob/main/23_runner/src/main/scala/runner/LevelGenerator.scala) перевіряє прохідність кожного зрізу **ізольовано** (`isSolvable`: на зрізі існує хоча б одна смуга з хоча б однією безпечною стійкою). Але в `Engine.scala` можливості маневру за один тік обмежені фізикою переходів:

```scala
val (nextLane, nextStance) = appliedAction match
  case Action.MoveLeft    => (hero.lane.left.getOrElse(hero.lane), Stance.Running)
  case Action.MoveRight   => (hero.lane.right.getOrElse(hero.lane), Stance.Running)
  case Action.Jump        => (hero.lane, Stance.Jumping)
  case Action.Duck        => (hero.lane, Stance.Ducking)
  case Action.KeepRunning => (hero.lane, Stance.Running)
```

З цього коду випливають **два жорсткі обмеження між сусідніми тактами**:
1. **Неможливо одночасно змінити смугу та стрибнути/присісти:** команди `MoveLeft` і `MoveRight` змінюють смугу, але **завжди переводять героя у стійку `Stance.Running`** (яка займає висоти `Low` та `Mid`). Не існує дії «перестрибнути на сусідню смугу».
2. **Бічна швидкість — щонайбільше 1 смуга за тік:** щоб переміститися з `Lane.Left` на `Lane.Right`, потрібно **два** послідовні тіки (`Left -> Center -> Right`).

#### Схема пастки для короткозорого бота (який дивиться лише на 1 зріз уперед):
```
Поточний стан (тік t): Герой на Lane.Left
                                │
                                ▼
Зріз t+1:  Lane.Left чиста (і там лежить монета), тому бот залишається на Lane.Left
                                │
                                ▼
Зріз t+2:  • Lane.Left заблокована повністю (перешкоди на Low [0] + High [2] — ні пробігти, ні присісти, ні перестрибнути)
           • Lane.Center має бар'єр на землі Low [0] (прохідна ЛИШЕ у стрибку Jump, але не в Running!)
           • Lane.Right повністю чиста (тому isSolvable(t+2) == true)
```

* **Чому короткозорий бот гине на `t+2`, хоча обидва зрізи прохідні:**
  * Перебуваючи на `Lane.Left` на тіку `t+1`, бот бачить глухий кут попереду на `t+2`:
    * Залишитися на `Lane.Left` (`KeepRunning`, `Jump`, `Duck`) — гарантоване зіткнення на `Lane.Left`.
    * Перейти вправо (`MoveRight` на `Lane.Center`) — `MoveRight` примусово ставить героя у `Stance.Running`, і він врізається у бар'єр `Low [0]` на `Lane.Center`!
    * Дістатися до чистої `Lane.Right` за один тік із `Lane.Left` фізично неможливо.
  * Щоб вижити на `t+2`, бот мав **ще на кроці `t -> t+1` заздалегідь перейти на `Lane.Center`**, щоб на кроці `t+1 -> t+2` або виконати `Jump` уже на `Lane.Center`, або перейти далі на `Lane.Right`.
* **Інженерний висновок:** `ReflexBot` (горизонт 1 зріз) не здатний бачити такі пастки. Саме тому `StrategicBot` має будувати граф досяжності на кілька кроків уперед (`upcoming`), де перехід із вершини `(lane, stance)` на кроці `k` до вершини на кроці `k+1` дозволений лише за правилами `Engine`.

### Помилка 3: Перевищення бюджету часу при експоненційному Backpressure
* **Симптом:** У режимі `benchmark` бюджет на тік зменшується за формулою `100 мс * exp(-t / 50)` до `500 нс`.
* **Чому повний перебір не вкладається в ліміт:** Перебір усіх траєкторій дерева глибиною 8 кроків має складність `O(3^8) ≈ 6561` операцій. При бюджеті у 10 мікросекунд такий розрахунок не встигає завершитися, виникає Timeout і застосовується резервний хід `KeepRunning`.
* **Функціональне вирішення — адаптивний вибір евристик:**
  * Рефлекси: `O(1)` — перевірка 1-го зрізу.
  * Жадібний вибір: `O(K)` — оцінка лише безпечних монет.
  * Стратег: перевіряє `observation.timeBudgetNanos` і динамічно зменшує глибину пошуку при падінні ліміту часу.

## 6. Контрольні питання для самоперевірки

<details markdown="1">
<summary>1. Чому функція decide(observation: Observation) повинна повертати дію для НАСТУПНОГО тіка (t+1), а не для поточного (t)?</summary>

Тому що на тіку `t` герой уже займає певну смугу та стійку, взаємодіючи зі зрізом `t`. Щоб змінити смугу або підстрибнути над бар'єром на зрізі `t+1`, імпульс руху повинен бути розрахований і переданий моторам заздалегідь під час такту `t`.
</details>

<details markdown="1">
<summary>2. Чим відрізняється поведінка Option[Lane].getOrElse від конструкції if/else?</summary>

`Option` виражає відсутність значення на рівні системи типів, позбавляючи від магічних констант і перевірок на `null`. `getOrElse` — це ідіоматичний вираз безпечного fallback: якщо повернуто `None`, використовується значення за замовчуванням без ризику `NullPointerException`.
</details>

<details markdown="1">
<summary>3. Яка обчислювальна складність у ланцюжка MajorityBot: map -> groupBy -> view.mapValues -> maxBy?</summary>

Оскільки кількість ботів фіксована (`N = 3`), а кількість можливих дій скінченна (`M = 5`), складність мажоритарного вибору становить константний час `O(1)`. Це забезпечує передбачуваний час відгуку в умовах жорсткого Backpressure.
</details>
